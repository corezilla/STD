# 项目自定义规范与强制索引

## 1. 目录与入口

项目自定义的编码、测试、文档和开发流程规范，默认放在 `docs/00_management/standards/`。
该目录的 `README.md` 是强制总索引；项目根README靠前的STD说明中必须链接它，并要求作者或Agent
开始任务前先读索引，再读本任务适用的生效规范。不能仅依赖文件搜索、旧会话或特定工具配置。

```text
README.md                              # 靠前链接项目规范总索引和已采用STD
docs/00_management/
├── standards/
│   ├── README.md                      # 强制总索引
│   ├── coding-standard.md             # 按需创建的规范
│   ├── testing-standard.md
│   └── documentation-standard.md
└── std-tailoring.md                   # 已批准裁剪/覆盖决定，名称为示例
```

可复制[总索引脚手架](../templates/_shared/project-standards-index.md)和
[单份规范脚手架](../templates/_shared/project-standard.md)。脚手架不新增catalog类型或设计层级，
不强制额外metadata；已有文档身份及控制字段应复用，不建立两套版本。
没有自定义规范时也保留总索引，明确“当前无项目自定义规范，遵循已采用STD”，不造空规范。
已有合理目录可保留，但根README须指定唯一实际索引，不自动搬迁历史文件或维护两份规范。

## 2. 必须登记的内容

每份规范必须登记规范ID、名称及文件链接、版本、状态、适用范围、触发任务、Owner，
以及STD关系和生效/替代决定。字段与规范正文及已有metadata一致；状态沿用项目文档控制词汇。
每份规范标题后必须反向链接总索引；总索引必须链接项目README的STD入口。
读到任意规范后，作者须回到总索引确认其他适用项，不能把当前文件视为全部项目规则。

触发任务须可判断，例如“修改Python源码”“编写测试或报告”“修改公共接口”；不能只写“开发相关”。
全项目规则标明所有任务适用，局部规则明确目录、对象或操作边界。草稿不自动生效，
废止项标明替代规范或明确无替代项，避免旧引用误导。索引只维护导航和适用性，不复制正文。

## 3. 与STD的关系

项目规范可以补充或细化已采用STD；已有STD条款只引用，不重复维护。
改变STD要求时，必须明确STD基线与条款、改动、范围、理由、风险和批准记录，并引用已有
`management.tailoring` 裁剪决定或对应ADR。未经批准不得覆盖STD；不得笼统声明“项目规范一律优先”。
项目规范之间或与STD冲突时，记录具体位置并交有权责任方裁决，不能自行挑选更宽松的规则。
规则不扩大当前用户授权，不授予额外访问或破坏性操作权限。

## 4. 交付检查与阻断项

新增、移动、改名、升级或废止规范时，必须在同一变更中同步索引、反向链接和受影响引用。
以下检查任一不满足，不得判定规范索引交付通过：

1. 从项目README靠前入口打开总索引，逐项打开规范，并从每份规范开头返回总索引。
2. 对照规范目录与项目已有规范清单，确认无未登记文件；目录外共置规范也必须登记。
   索引、附件和历史证据不是独立规范，须明确性质，不能借改名隐藏未登记规则。
3. 规范ID唯一，文件存在，版本、状态、Owner、范围和触发任务与正文及已有metadata一致。
   同范围不能有相互冲突且同时生效的两份权威规则；明确新旧版本替代关系。
4. 草稿、废止、无自定义规范等状态明确；链接可打开不等于规则的生效范围清楚。
5. 改变STD要求的条目有具体批准依据；移动和废止后核查旧引用，不能留下断链或两份独立维护正文。
6. 用一项真实任务演练从索引识别必读规范，确认新作者能判断要读什么、做什么。

项目现有链接检查工具可辅助检查；结构测试不能替代适用性、冲突和批准语义评审。
本规则提供规范和脚手架，不宣称现有校验器已能自动验证上述全部项目规范要求。
