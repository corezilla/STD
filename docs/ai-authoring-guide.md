# 通用 AI 编写指南

版本：0.2.0-draft.2 · 日期：2026-09-12 · 状态：方法草案，待各类实际写作任务验证

本指南是 STD 的 AI 写作入口，适用于设计、计划、分析、规格、报告和操作文档。它说明 Agent 如何核查输入、解决写作背后的问题、成文并检查；**模板规定交付内容，专项指南说明该类内容怎样设计或取证，项目事实及已批准决定提供实际输入。** 指南不是产品决定、执行授权或新的审批平台。

通用方法由[原系统设计 AI 指南](ai-system-design-authoring-guide.md)提炼。系统指南保留系统层设计方法，其他类型不必先读完整系统指南；项目复盘和保密参考不随方法迁入。各指南独立版本，不因指南更新就升级 STD 发布版或模板版。

## 1. 选择入口与阅读范围

初次完整编写：先读本指南，再根据实际交付物读取**一个主专项指南**、项目已采用的模板及其全部编写建议；最后读该任务需要的项目来源。不是先读全部指南，也不是按项目名称选模板。续写或局部修改先读现有记录、对应方法和当前差异，只检查受影响内容及直接依赖，不重跑完整写作流程。

## 2. 固定输入，不把教学内容当成项目事实

先核查项目、文档对象、采用模板、事实来源、现有正文与图件、输出路径、允许的修改范围和保密边界。保持用户已有未提交修改，恢复任务时重新读实际文件，不能用旧聊天记忆覆盖当前内容。局部任务不能借整理文档批量迁移项目、改公共契约或变更代码。

建立轻量事实底稿：记录影响结论的主张、来源路径/版本/必要的 commit 或摘要、适用配置和拓扑、状态、影响位置及责任角色。只保存实际需要的证据，不为每句话新增 sidecar。区分已确认决定、可核查现状、分析假设、作者建议四类输入。两个版本的有利数据不能拼成一个不存在的配置；冲突应并列记录并指向有权裁决者。

未知项要能处理。例如“离线使用是否允许依赖远程许可服务？这决定启动和维护边界，需产品责任方在部署方案定稿前决定”；不能只留“环境 TBD”。可基于明确假设推进独立分析，但依赖未定前提的保证仍未闭合。来源真实存在也不代表相关：要打开实际字段、行为、测量条件或决定记录，而非只检查链接能访问。

保密资料仅在授权范围内处理；不发送到外部绘图、生成或发布服务，不复制进公共模板、示例、日志或待发布资产，不作为训练材料提交。教学例子必须声明虚构，用通用对象说明方法，不能改名后复述保密产品设计。是否可以保存来源、生成记录及临时预览，也遵循该资料的授权。

## 3. 把模板变成可执行的工作包

逐节读取模板帮助，将适用内容转换为“要解决的问题—输入/前置决定—正文或图表—使用者—完成检查”。按依赖组合成工作包，不平均分配字数，不照抄目录作为计划。每包记录简短 ID、目标、输入、产物位置、检查方法、状态、缺口与下一步；复用项目现有记录，不开发新的写作工作流平台。

正文写在帮助块之外。帮助折叠或删除后仍需自包含；将“应描述接口”改成“本系统描述接口”不算填好了内容。模板不是信息上限：实际问题需要时可增补子节、推导、图例或代表场景，但保留必需信息项及其去向。章节裁剪引用模板适用规则和项目既有 tailoring 决定；资料缺失不是 N/A，待批裁剪不是已经免除要求。

执行按“读输入 → 解决问题/核对证据 → 成文 → 检查与修正 → 保存并继续”的闭环推进。一个内容包包含实际正文、必要图表、依据、未决事项和本次检查结果；没有复杂关系不硬画图，需要图却仍是占位则该包尚未完成。阶段通过通常是作者自审，不默认每一步都等用户批准。真正改变产品范围、权利或关键政策时才进入既有决定流程。

长任务每包结束保存来源基线、术语、稳定标识、已完成位置、未闭合问题、检查结果和下一步；续写先核对实际差异。变更一个核心决定时同步找出相关职责、图、过程、预算和验证项。不得用计划或阶段汇报代替写作，不默认创建后台任务；任务停止时保留当前结果，未经重新授权不继续处理。

**先区分文档性质。** 设计和计划解决未来如何工作；报告记录实际发生了什么；决策记录表达有权者作出的决定；操作文档给读者可执行的步骤。报告不能用预设计补造历史测量，计划不能写成已执行结果，作者建议不能自动成为已批准决定。各专项细化这些边界。

设计工作包需要接上[统一映射规范](interface-data-mapping-standard.md)：先读项目接口总目录及实际源，
沿正常/异常/维护路径列成员，区分复用、扩展、冲突和缺失；复用/分配稳定 ID 后，先设计全字段与行为，再落盘机器契约。
系统先登记机制文档清单和预定文件名，按依赖逐份编写；Planned 不是可访问来源，不用空文件通过检查。

多份机制连续或并行成文时，使用[机制专项 §10](ai-guides/system-mechanism.md#10-批量编写与跨文档复审)
固定本批输入和共享文件责任，再做受影响文档及组合场景回查；不为每份文档重新检查 STD 最新版本。

## 4. 不清楚时做预设计，而不是扩写口号

对设计/计划中讲不出机制、取舍或验证方法的部分，先列本节必须解决的问题。简短预设计按以下顺序展开：输入与约束 → 真实可行选项 → 正常及失败推演 → 推荐方案、依据与代价 → 未决项及下一项缩小问题的动作。只有一种可行方案时解释其他方案为何被排除，不凑虚假备选。复杂分析复用 `evaluation.technical-analysis`，无需新增模板种类。

例如“支持并行测试”尚不是设计。先确认并行对象共享哪些设备、端口、目录或状态；比较分区、串行或已有隔离能力；推演一项超时是否影响另一项；决定独占资源、隔离标识和清理责任。仍未知时记录需要核查的实现/测量、选择判据、不满足时退回哪项决定及受影响工作。独立部分可继续，不能因为一个待决项冻结整个文档。

获得依据且符合决定权限的方案要回写正式正文、约束与验证方法。分析保存理由，正式设计唯一维护采用的保证；不让预设计和正文形成两份相互竞争的规范。机制未决定不能称该节设计完成；机制清楚但尚未实现/实测可以如实保留，不必为消灭 NOT_RUN 无界扩写或执行未授权实验。

对报告，缺少证据的正确动作是查找获准来源、标明缺失/不可复现并请求补证；不是编写一个“合理的实际结果”。对评审与 ADR，没有有权者的决定就保持建议或待决，不用作者自审代替签署。指南要求设计试验方法不等于授权执行试验。

## 5. 写出可使用的正文与承接结果

连续正文解释动机、原理、取舍和边界；表格表达精确映射、比较、预算或状态；步骤表达先后依赖；图表达空间、组成、流向或状态关系。不要把一切压进四列表，也不要用目录、模块名或大量链接代替解释。关键段落应能沿一个代表输入说明谁在什么条件下做什么、输出意味着什么、失败如何处理。

每个适用节收口时检查：本节实际决定/确认了什么，依据是什么，下游必须遵守什么，还能自行决定什么，怎样检查承接结果。答案来自正文和推导，不另填五句口号。报告中的“确认”必须指实际证据，不能变成新的设计政策。已有机器契约只引用唯一定义和必要语义，避免复制后产生不同字段表。

设计的下游输入应绑定约束标识、适用条件、承接方、分配预算/行为保证、实现自由度、本地及组合验证责任和变更影响。局部通过不等于组合通过，共享预算不能重复分配。下级无法满足约束时返回原决定责任方，不自行改大预算或降低共同保证。

控制篇幅靠删重复，不靠页数配额。逐段问删掉后会失去哪一个事实、判断或过程；若没有损失，合并或删除。多场景或复杂失败路径需要足够展开，不以“简洁”为理由省略。概览应自包含，交叉引用帮助深入，不能让读者追完十份文件才知道本文用途。

成文时同步机器定义、完整字段/签名阅读视图、目录来源与正文回链；公共类型引用原 ID。
下游逐成员声明提供/消费的 version/revision/hash、模块/实际代码或 NOT_IMPLEMENTED，以及设计 V→Case/环境/Run。
修改后实际做双向定位和字段/签名/错误/版本核对，再用完整正常与失败输入模拟双方；参考
[可运行正反例](examples/interfaces/README.md)。不能用“生成成功”掩盖旧错误/流程，不能把未承接或未运行项从分母删除。

## 6. 分开状态、依据和结论

正文先解释内容，再紧邻注明适用版本、配置和成熟度。文档批准、架构视图、能力实现与验证结果是不同维度，不能排成一条升级流水线。沿用项目和适用模板的词表；设计类常用：

- 文档状态：如 Draft、In Review、Approved，按文档控制规则。
- 架构视图：`Current / Target / Transitional`。
- 实现状态：`Planned / Partial / Implemented`。
- 验证结果：`NOT_RUN / BLOCKED / FAIL / PARTIAL / Verified`，绑定被测范围、输入与通过判据；工具原始 PASS/FAIL 记录原样保存。

代码存在但未测试可以是 Implemented / NOT_RUN；只验证某个模式不能把全模块写成 Verified。结构检查 PASS 不证明内容合理，文档 Approved 不证明产品性能。未实施的推荐设计仍可写清原理，不必每段堆满状态词。

数字必须有单位、作用域、版本/配置、负载条件、依据与误差/限制。区分 Modeled / Simulated / Measured；估算、模拟、单元测试、系统实测不能互换。多个数字参与推导时先统一条件和单位，不用平均值替代峰值，也不把器件理论值写成产品可交付值。

## 7. 绘图与样式复用

先确定图要回答的问题，再列实际对象、关系、边界与适用状态。少量精确映射用表更清楚就不画。参考[图形样式目录](../templates/diagrams/README.md)，按专项选择已有 SVG、Mermaid 或项目可维护图源；已有合格图不强制换格式，不要求凑齐图的数量。

### 7.1 从语义到图件

给必要图建立轻量图卡：图号、说明任务、来源基线、对象及关系语义、Current/Target 状态、对应正文/约束、图源和展示位置。先核实拓扑与职责，不能让绘图工具替作者设计。系统组成、物理部署、过程交互是不同视图；不要把同一框一会儿当软件一会儿当设备。

选择图种后按信息层级安排分组。组成图用包含关系；交互图给线标方向及数据/命令/信号意义，跨责任边界关联接口或操作标识。状态图固定一个对象，说明触发、Guard、动作和退出条件。若协议未决定，写“逻辑交接，协议待定”，不猜常见协议。未来对象和控制线不能共用同一种虚线含义，重要区别不能只靠颜色。

复制获准样式到项目规定的资产目录，改对象名称、分组、关系、图例、标题/说明及引用，不只换项目名。示例参数和协议不会随样式复用成为项目设计。修改关系后与正文同一代表输入逐步对照，复杂时分图，不无限缩小文字。

### 7.2 工具、来源与渲染验收

原生工程图保留 SVG、Mermaid 或绘图工具源；生成式插画保留原始位图及获准保存的提示词、来源和边界说明，不声称具有不存在的 SVG/三维源，也不承诺重生成像素一致。保密材料不得传给外部服务。工程协议、端口和连线不能以生成式图片为技术依据。按工具自身技能与权限操作，不假设插件一定存在。

修改源后同步展示文件，在实际 Markdown 阅读器或等效导出中按正文宽度查看中文换行、标签、箭头、遮挡、裁切和状态图例。先只读图与图注复述，再对照正文核查；脚本成功、文件存在或源码语法通过不等于渲染验收。无法查看时明确未检查，不声称完成图。没有源变化无需重生成既有图。

图前提出要解释的问题，图注写范围，图后解释关键原理与取舍。图和正文使用稳定名称/标识，变更时一起维护。STD 的小型文档资产使用 `docs/assets/`，项目实例使用项目约定目录与相对引用，不依赖作者机器的 STD 绝对路径；临时预览不混进发布包。

## 8. 自审、修正与交付

每包检查实际内容，不只勾“章节存在”：沿正常输入及重要边界/失败条件推演，核对来源、数字、状态、图文一致和下游承接。完整稿再检查范围覆盖及跨章节组合；局部稿明确本次不是全篇复审。问题写具体两处、矛盾和影响，修正后记录复验结果。

自审与独立评审分别报告。没有其他读者或真实批准记录，不声称独立通过；Agent 不能自行把 Document Status 升为 Approved。结构、链接、数值和渲染可用工具辅助；设计可行性、报告可信度、失败闭合与组合约束仍需内容审查，工具通过只按实际覆盖范围报告。

交付唯一正文、实际维护的图源/原始位图和已检查展示形式、必要依据、未决项、完成范围及检查结果；优先复用现有计划和记录，不要求每项新增文件。明确区分“内容已成文并自审”“方案待实现/实测”“关键设计仍未定”“报告证据缺失”。不要把阶段稿称为全项目完成。

提交、push、发布、RAG 收录、环境/硬件操作和 Runtime Activation 依用户及项目权限分别判断，不由写作任务或通过检查自动授权。本指南也不自动启动协作 Agent、监控或后台任务。

## 9. 采用、版本和后续验证

项目级 STD 采用版本仍记录在项目 README 和 `docs/std.lock.json`；单文档遵循所用模板自己的 ID、版本及哈希，见[版本规范](versioning.md)。普通修订没有用户明确要求时，不主动检查模板是否有新版，不升级项目采用记录。指南是写作方法，不在单文档封面新增 STD Version 或一套必填指南版本锁。

本文及专项可以独立修订；公共方法只在本文维护，专项保留本类型问题、输入、顺序、图例、收口条件和下游接口，不全文复制公共规范。章节内编写建议仍留在模板，不能因拆出指南而删除。引用涉及章节编号时绑定适用版本，不伪称工作稿已包含在旧 commit 或发布标签。

本轮建立 13 类入口和基础方法。已有系统/机制的深入案例予以保留，其余专项需在实际文档中试写验证，不能因目录覆盖 46 个模板就声称所有指南已实证有效。后续按真实返工原因调整对应方法，不为形式对称无限增加指南或模板章节。

可复用任务说明：请给出项目与交付物、采用模板、实际输入、现稿及输出路径、修改范围与权限；Agent 先按本指南和主专项建立相称工作包，然后产出正文并自审，不止于交计划。缺失决定说明影响和具体问题，未知证据不编造。
