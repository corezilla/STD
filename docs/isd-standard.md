# 软件实现规格设计（ISD）规范

版本：0.2.0-draft.1。状态：Draft。

## 1. 定位与适用条件

ISD（Implementation Specification Design，实现规格设计）把已确定的模块方案落实到文件、内部类型、函数、算法、执行上下文和测试。它是软件模块的可选实现视图，不新增对象层级、模块编号或必经审批阶段。

默认一个模块一份ISD，可覆盖多个源文件及头文件。不按文件数量强制建文；复杂模块只有在内部实现单元边界清楚、可分别维护时才拆分，保留一个入口列出分卷范围和唯一责任。内部单元沿原模块编号，用局部名称区分。

采用方式：

| 现有设计情况 | 交付方式 |
|---|---|
| 模块设计已达到本规范深度 | 直接兼作ISD，登记信息项到章节的映射，不另建重复文件 |
| 模块行为已明确，但精确文件/symbol、私有表示及语言级步骤尚未细化 | 使用 `design.implementation` 建独立ISD |
| 只有少量局部细节缺失 | 补入模块设计相应章节 |
| 公共行为、接口或资源政策未定 | 返回原模块/接口/上级设计解决；ISD不得自行改变跨模块决定 |

`design.definition` 继续是模块详细设计模板；新增ISD不削弱其已有要求。兼作ISD不必换Template ID或文档版本体系，但内容改变按项目版本规范处理。

独立成文时按下表逐项建立承接矩阵，填入真实固定来源（Document ID/版本/锚点及提交或摘要），不能只填“见模块设计”。模块设计决定外部可观察行为、公共接口、算法规则、不变量、资源预算及失败语义，并给出验证规格；这些不能推迟为“ISD再定”。ISD决定准确文件和symbol、私有类型与语言级表示、调用/锁/清理步骤、装配点及测试入口。模块已经包含后者则兼作ISD；独立ISD无需重复上游规则，但必须展开真正影响实现正确性的细化，不只是文件清单。

| 上游信息项 | 固定来源 | ISD必须细化 | 权威位置 | 实现自由度 | 验证位置 |
|---|---|---|---|---|---|
| 用途、范围、共同保证 | 模块用途/Constraint | 本次实现覆盖、入口及差异 | 原模块行为章节 | 仅明确允许的局部实现选项 | 原V/Case及宿主组合项 |
| 公共数据、签名、错误 | 原成员ID/机器源基线及模块阅读视图 | 参数传递、校验点、返回构造、字段转换和寿命 | 字段/签名仍在原机器源；行为在原正文 | 不改字段、错误优先级或可见行为 | 原成员的V/Case；补局部向量 |
| 内部结构和算法 | 模块结构/算法规则 | 私有helper、语言类型、边界计算、调用顺序 | 模块维护算法决定；ISD维护实现细化 | 不改变结果、复杂度约束及并发保证 | 原算法V；边界/溢出/交错Case |
| 安全、权限和维护 | 模块§11及原指标/权限规则 | 函数检查点、拒绝出口、脱敏字段、日志/统计触发与宿主交接 | 原规则和口径不复制；ISD维护落点 | 不新增授权、诊断或日志机制 | 原安全/维护V；拒绝/不泄露/口径Case |
| 生命周期、资源与环境 | 模块生命周期/预算基线 | 锁/清理、阶段计时、额度操作、宿主hook | 原模块政策；ISD实现步骤 | 不重分配上限或放宽停止条件 | 局部Case及上级组合验证分开 |
| 文件、构建与验证交付 | 模块实现组织/原V与Case | 精确文件/symbol、编译链接、测试入口与任务依赖 | ISD细化；原登记表索引 | 文件拆分等仅在授权范围内 | 原验证表增加向量/入口，不另复制Case |

引用可以替代重复字段表、已完整算法或测试定义，但必须保留理解本实现所需的约束摘要和准确入口。本层新增的私有表示、语言陷阱、调用/清理顺序及装配不能只引用上游。当模块已有全部细节时直接兼作；独立ISD已拥有的实现细节由模块链接引用，模块仍须自包含地解释其行为与方案。移动既有规则的权威位置须显式记录并同步引用，不因新建ISD默默转移。

## 2. 组织、标识与来源

独立稿建议名 `<MODULE>_ISD.md`，位于 `software/<component>/docs/isd/`；无组件目录时默认 `docs/50_implementation_design/`。项目可沿用已批准路径。旧稿先核对内容和来源，再决定合并、保留或标记被替代，不自动搬迁或删除。

metadata 使用 `template_id=design.implementation`、`design_level=module`、`domain=[software]`。模块对象ID不变。`parent_document_id`仍指向直属父对象的设计（软件系统或软件子系统），不指向同模块的模块设计，也不把分卷当新子对象。正文的“模块设计来源”表另记录同对象模块设计Document ID、版本、路径/锚点及摘要/提交。

同一模块可有模块设计和ISD两个Document ID；每项规则只能有一个权威维护位置。兼作模式的入口直接指向模块设计，并列出本规范各信息项的承载章节。分卷需在入口列清交叉调用和共享内部类型，避免两卷定义同一结构。

### 2.1 机器登记与检索

采用本修订后，软件模块metadata登记 `design_object_id`（项目内既有模块ID）和 `implementation_specification`；独立ISD登记同一个 `design_object_id`、`implementation_view_of_document_id`（对应模块设计Document ID）及 `volume_of_document_id`（入口为null，分卷为入口Document ID）。分卷不得嵌套，所有视图与模块的project、对象ID、直属parent必须一致。只有一个现行模块设计和一个现行独立ISD入口；superseded/retired历史稿不作为现行入口。关系只在显式输入集合中查找，不读取邻项目。

`implementation_specification`字段固定为 `mode/document_id/coverage_mapping/reason/decision_ref`：

| mode | document_id | coverage_mapping | reason / decision_ref |
|---|---|---|---|
| embedded | 模块文档自身ID | 本文件信息项锚点 | 无豁免时null/null |
| separate | 独立ISD入口ID | 入口及直属分卷的信息项锚点 | 无豁免时null/null |
| not_required | null | 空数组 | 非空理由及已接受决定的DocumentID#anchor |
| missing | null | 空数组 | 可记录缺口；不能通过交付检查 |

每个coverage_mapping对象包含 `item/document_id/anchor/applicability/reason/decision_ref`。
item全集为scope、structure、data、functions、algorithms、lifecycle、resources、security、persistence、verification，各一次；默认anchor为`isd-`加item，也可用已存在的明确HTML锚点。兼作时指向模块本身，独立时仅指向入口/直属分卷，不用上游链接代替本层落实。每个分卷必须被覆盖映射使用。
applicability为applicable或not_applicable；仅algorithms/security/persistence允许后者，须给边界理由、正文说明及已接受的tailoring/范围决定引用（DocumentID#anchor）。其余项始终须说明本层或宿主落实。引用的决定必须在检查输入中，状态accepted/released且有内容；自动检查不能证明批准权限或理由合理。

例：模块M201的独立稿为FRAME_ISD，模块登记mode=separate/document_id=FRAME_ISD，ISD登记implementation_view_of_document_id=FRAME_MODULE、design_object_id=M201、volume_of_document_id=null；两者parent_document_id均为PARSER_SYSTEM。一个覆盖项可写：

```json
{"item":"data","document_id":"FRAME_ISD","anchor":"isd-data","applicability":"applicable","reason":null,"decision_ref":null}
```

这只是一个条目，不是完整十项登记。生成器可用`--design-object-id M201 --implementation-view-of-document-id FRAME_MODULE`建立关联；分卷另加`--volume-of-document-id FRAME_ISD`。未提供时生成空关系草稿，交付前必须补齐。模块草稿默认mode=missing，不从正文长度猜测兼作，不强制给旧项目升级。

## 3. 必需信息与深度

| 信息项 | 必须交付 | 不充分的替代写法 |
|---|---|---|
| 目标与范围 | 场景、代表输入输出、继承规则、本次版本范围、非目标 | 文件名清单 |
| 当前实现与目标差异 | 基线、保留/新增/修改/删除的位置及原因；未知路径标Planned | “基于现有代码改造” |
| 代码组织 | 文件、内部组件、调用及类型依赖、归属构建目标 | 把函数当新模块编号 |
| 数据与ownership | 具体字段、类型、单位、初值、不变量、分配/借用/释放责任 | “采用统一结构” |
| 函数与接口 | 关键签名、完整输入输出、前置条件、错误、幂等及副作用、调用者 | “参数见代码” |
| 处理与算法 | 逐条件流程、关键算法伪代码、可手算样例、失败出口 | “校验后执行” |
| 并发与生命周期 | 执行上下文、锁范围/顺序、事件事实、取消、迟到和安全释放 | “加锁保证安全” |
| 持久化与数据升级（适用时） | 事务边界、持久提交点、崩溃恢复入口、源/目标数据版本、转换/切换步骤与失败出口 | “重启自动恢复” |
| 资源与装配 | 峰值构成、上限、超限行为、构建依赖、初始化/销毁和实际接入点 | 无口径的容量常数 |
| 安全、权限与可观测性 | 原规则→检查函数/字段→拒绝或上报出口→测试；宿主责任的调用点和交付信息 | “统一由平台保障” |
| 验证与交付 | Rule/成员→V→Case→Vector→Oracle→环境/Run、任务依赖与完成条件 | 只有测试名称或文档PASS |

不要求逐行描述代码。简单getter可分组；有外部副作用、共享状态、关键分支或资源转换的函数必须单独说明。公共结构和协议引用原 `interfaces` 权威，不抄出新版本；本模块私有类型可以在ISD定义，并指定未来代码权威及同步方式。

每个重要过程有流程图或时序图，图中的Guard写明来自哪个调用、事件或字段。图后用同一输入走通成功、边界和失败；复杂异步路径另覆盖取消、迟到、依赖失败及未知访问。不为凑章节新增线程、队列或重试机制。

每个重要算法有算法图、正文和具体输入推演，按需配伪代码，检查语言整数提升、溢出、未对齐访问和默认库行为。过程图可在真实覆盖算法判断时兼作，不用图数量替代内容检查。

持久化模块承接上游事务、恢复及升级政策，ISD定位具体开始/提交/回滚函数、原子范围、事务外副作用、持久提交点与响应点；提交结果未知时核对原权威记录，不推定失败或重新执行。给出崩溃后的恢复入口、记录版本及判定、重复恢复条件。已有数据的升级转换明确源/目标版本、转换函数、校验/切换点、中断后的继续或回退条件和失败出口；不得在ISD重新制定兼容政策。无持久化不虚构数据库，交由宿主的范围仍给实际交接责任。

故障验证允许依赖替身、受控故障点、可控时钟及调度。记录正常入口建立的前置事实、注入位置/时刻、依赖返回或中断语义、独立观察与复位；禁止直接修改业务终态来伪造流程通过。旧数据fixture可验证恢复/转换，但须标注人工构造及来源，不能声称已覆盖其生产过程。适用时覆盖提交前、持久提交后响应前、恢复中断及数据升级切换失败；模型故障注入不代替真实进程/存储耐久性证据。

资源与时间预算沿用模块设计，不重新制定：固定环境版本、硬件/虚拟化、依赖、数据规模、冷/热启动及并发峰值；将初始化、复位、启动、运行、停止、清理的预算和总期限映射到实际函数、计时点、额度申请/归还和超限出口。LLM 能力、上下文/输出、请求量、并发/排队预算按适用性承接。无独立生命周期的库引用宿主责任，不虚构启动器。

安全与维护按适用性落实到现有函数：身份来自哪个可信上下文、授权在副作用前哪里检查、服务失败或拒绝返回什么；敏感字段在哪里脱敏、哪些内容禁止输出；日志/指标/trace的触发、关联字段、单位、窗口、重置与错误上报由谁执行。诊断入口承接既有权限与影响范围，不改变业务结果。无独立权限、日志或诊断能力时，仍写清向宿主返回的结构化错误/关联信息、宿主接收入口和验证责任；确实不适用的规则给边界理由，不新增机制。

## 4. Agent导航与双向映射

复用项目现有模块/接口/文档登记表，记录模块ID→模块设计→ISD（或兼作入口）→文件/symbol→验证项。本文不新建第二套全局ID或运行时注册表。

每个消费/提供的公共成员记录原成员ID、源路径、selector/锚点、version/revision/hash、角色和适用backend；从成员能找到实现责任，从函数也能回到成员。函数尚未实现时写Planned路径/符号和NOT_IMPLEMENTED，不填写伪造行号。生成代码登记生成源与目标，禁止把手写副本当权威。

Planned路径/符号只存在于人读计划栏；机器目录在未实现时必须保持 `location=null`、`symbol=null`，仍保留成员、role/module/backend、源基线和原V/Case，`runs=[]`。同一成员的模块设计与ISD两处承接描述是同一条责任链，不是两个backend或两条实现。实现后核对实际文件和symbol再原位更新该承接行；验证仍可not_run，只有真实Run才能更新运行结果。契约未改变时不得用代码hash覆盖source_sha256。完整转换示例见[计划与机器目录](examples/isd-planned-mapping.md)，模块到代码的连续示例见[FrameDecoder](examples/isd-frame-decoder/README.md)。

已有机器登记schema支持这些字段时使用原schema；不支持的项目先在现有映射表记录并提出schema变更，不能塞入未知字段后宣称机器校验通过。接口字段仍按[统一映射规范](interface-data-mapping-standard.md)定义。

## 5. 完成与变更

作者先按真实公开入口进行成功/失败/并发推演，再从编码者、接口消费者、资源与测试四个视角复核。能确定函数职责、完整参数、错误和清理，不需要编码者重新决定共同机制，才可作为对应范围的编码输入。

父链检查使用 `validate-design <完整设计目录> --check-design-hierarchy --json`，同模块设计不能作为 ISD 的父对象；缺父输入时报告未能核对，不虚造对象。历史纯软件总体设计采用 design.system 时须明确 software 领域；领域角色仍需正文确认，检查器不能仅凭枚举证明业务归属。

交付前显式运行 `python3 scripts/validate-design <完整设计目录> --check-isd-delivery --json`。该模式同时检查父链、同对象视图/反向登记、唯一入口/分卷、十项覆盖及正文非空。入口需唯一`isd-handoff`锚点及完整六列矩阵；适用的security/persistence锚点需七列落实表；verification需八列表（Rule、V/Case/Vector、输入、Expected、Actual/Evidence、Verdict、测试入口、Run）。每Vector一行；未执行允许Actual=NOT_RUN、Verdict=NOT_RUN、Run=NOT_RUN，已执行PASS/FAIL必须有实际结果/证据及Run ID。模型Run不能当产品Run。

锚点采用`<a id="isd-data"></a>`等写法，后接本项正文/表格，下一标题或锚点结束范围。表格单元格含竖线时用HTML实体避免歧义。检查忽略折叠帮助和注释；表头/占位不能当交付，不能用长篇写作说明充数。基础校验允许空草稿；交付检查PASS也只说明关联与槽位完整，不证明语义、证据真实性、覆盖充分性或可编码质量。需人工复核实际设计，旧版本不自动启用本检查。

Document Status、实现状态、验证结果分别记录。Planned/NOT_IMPLEMENTED允许交给开发；核心规格未定必须列明确阻断范围及解决动作，不能用NOT_RUN掩盖。设计模型、结构检查和图渲染不证明产品运行正确。

未决项承接通用规范：记录Owner、最晚关闭阶段/截止Gate、分析或决策引用、所需输入、下一步选择判据和关闭条件。可引用现有问题台账的稳定ID，不重复维护状态；引用处应能定位责任、期限与阻断范围。无人负责或未确定关闭Gate的关键问题不得视为已完成设计。

变更顺序为原规则/接口→模块设计→ISD→实现→测试与索引；同一次修改同步受影响项。局部实现发现共同方案问题时反馈原成员和具体反例，不私自放宽约束。旧ISD的“已实现”只对原基线成立，新接口未对齐前不得用于新版本编码。
