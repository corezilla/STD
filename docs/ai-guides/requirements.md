# 需求与追溯 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`requirements.stakeholder-needs`、`requirements.conops`、`requirements.specification`、`requirements.traceability`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

取得客户/使用者及其他相关方原始需求、使用环境、已确认产品边界、适用约束、现有需求基线和验收责任。先分清“用户想完成什么”“系统必须满足什么”和“作者建议怎么实现”，不能把常见架构或模板例子当需求来源。

不把每条实现笔记提升为强制需求，也不以旧测试是否通过决定用户是否需要某能力。冲突的客户目标要记录影响和决定责任，不在编辑时静默删除其中一方。

## 2. 专项执行顺序

1. 从主要用户任务写出 Need 与成功结果，区分实际使用者、采购者、运维者和研发责任。
2. 用 ConOps 推演系统在环境中的正常/异常使用、工作模式和人机责任；维护操作不能替代主业务场景。
3. 将被确认的需求转成可验证要求：输入与前提、行为/响应、量化条件、边界/错误、判定方法，保留来源与优先级依据。
4. 将需求分配到设计与验证，检查覆盖和组合；追溯关系不是验证证据。
5. 变更时双向追查来源、设计、契约、用例与已有报告，更新受影响项而不是整体重编编号。

## 3. 不同模板的实际产物

| Template ID | 核心输出 | 常见错误 |
|---|---|---|
| requirements.stakeholder-needs | 相关方、任务、痛点、期望和约束的来源 | 直接给技术选型而没有需求 |
| requirements.conops | Current/Target 使用环境、场景、模式、人机交互及异常处置 | 只画内部模块或只写维护动作 |
| requirements.specification | 可区分合格/不合格的要求、条件与验证方法 | “高性能、易维护、实时”无判据 |
| requirements.traceability | Need→Requirement→Design/Contract→Test→Evidence 的关系与缺口 | 有链接就标满足，多个来源拼成一个版本 |

规格中的复合要求应拆到能独立分配与判定；拆分后保留组合目标，不能用局部条款都通过证明总体目标。重复、孤立、冲突和缺少判据的要求要分别标识。

## 4. 图例与写法示例

ConOps 适合逻辑应用场景/上下文图，可参考[图形目录](../../templates/diagrams/README.md)的应用图；不强制写实人物或部署照片。追溯通常用表更清楚，不画满页蜘蛛网。

虚构例：弱写法“查询应快速返回”。有效改写先确认查询负载、数据规模、并发与部署条件，再定义响应时延的起止点、统计口径、限值来源及超载行为；尚无确认限值时标为待定需求及决定责任，不随意填一个毫秒值。

需求写法示意：“在配置 C 与负载 L 下，从接收有效请求到返回完整结果的 P95 时延不超过已确认限值 T；过载结果按契约 E 判定。”C/L/T/E 必须在真实文档中有实际定义；保留符号却无定义仍未完成。

## 5. 完成检查与下游承接

从一项用户 Need 能找到系统要求、分配和验证方法；反向从关键设计/用例能找到依据。覆盖率按实际分母和关系类型报告，存在用例不等于执行，执行通过不等于客户验收。

交给设计者的输入不能含未声明的方案假设；交给测试者的要求应有独立判据。未知产品决定与可继续设计范围分开，未获确认的要求不擅自升级基线。
