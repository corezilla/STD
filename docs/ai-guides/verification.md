# 验证与验收 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`assurance.vv-plan`、`assurance.test-plan`、`assurance.test-specification`、`assurance.test-procedure`、`assurance.test-report`、`assurance.acceptance-plan`、`assurance.acceptance-report`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

读取固定需求/设计/契约基线、被测对象与配置、风险、测试环境和真实可用的控制/观测接口。先确定要验证哪个保证，以及不依赖被测实现同一逻辑的正确性判据。被测范围、模拟边界和生产环境不能混为一谈。

计划、规范、步骤和报告各有责任；测试完成不自动等于客户验收或上线授权。没有原始执行证据不能编写“实际结果 PASS”，缺测或不可复现按事实标记。

## 2. 专项执行顺序

1. 从每项关键保证反推输入构造、前提、观察点、独立 Oracle 和失败反例，覆盖正常、边界及主要错误。
2. 区分真实被测路径与替代依赖，确认控制动作实际命中哪里；模拟测试不得声称经过被绕过的硬件或外部系统。
3. 设计环境快速部署、复位、数据准备、并行隔离和安全清理，识别共享设备/端口/文件/状态，不能只写“自动化执行”。
4. 将用例转成可执行步骤及明确停止条件，保留构建/配置/随机种子、输入、stdout/stderr、退出码与产物。
5. 报告只汇总实际运行，分开预期/实际结果、未运行、阻塞和失败；解释未覆盖风险及验收责任。

## 3. 不同模板的实际产物

| Template ID | 负责什么 | 与相邻文档的区别 |
|---|---|---|
| assurance.vv-plan | 验证策略、层级、责任、覆盖和证据链 | 不写成全部 Case 步骤 |
| assurance.test-plan | 一批测试的范围、资源、环境、顺序和退出条件 | 计划不是执行报告 |
| assurance.test-specification | Case 的输入、覆盖点、预期行为、独立判据 | 规范不伪造实际结果 |
| assurance.test-procedure | 实际执行步骤、位置、前提、参数、记录及清理 | 不能仅列 Case 名 |
| assurance.test-report | 固定输入上的实际运行、偏差、缺陷和结论 | 保留失败/缺测，不能改预期迁就实现 |
| assurance.acceptance-plan | 有权验收方认可的范围、判据、责任和例外方式 | 不由测试作者自动批准 |
| assurance.acceptance-report | 实际验收活动、证据、遗留项和真实决定 | 没有签收/决定就不写已接受 |

实现前可评审语义、Schema、向量或参考模型；实现后才运行对应实现的契约测试，随后集成/E2E。不能形成“开发前先通过真实两端实现测试”的依赖循环。

## 4. 图例与写法示例

复杂夹具可参考[机制测试路径图](../../templates/diagrams/mechanism/test-path.svg)，标明控制、真实路径、观测、Oracle 及被替代部分；简单测试用短表即可。图中的延迟夹具只是一项虚构示例，不是项目已有能力。自动化流水线有阶段依赖时另画流程图。

虚构例：弱写法“构造 prompt，LLM 返回正确即 PASS”。有效规范先给 prompt/输入构造规则、模型与配置、预期约束、比较方法和不确定性处理；Oracle 可以基于固定期望、结构/约束校验或独立评判标准，但不能让同一被测代码无条件认定自身正确。

还要说明多次运行的统计判据与失败留存、并行请求隔离、复位是否清除缓存/会话、哪些环境事实被保存以复现。确切样本量和阈值需有项目依据，不从示例擅自指定。

## 5. 完成检查与下游承接

选择一个 Case，另一位执行者应能从基线部署到准备、执行、观察、判定和清理；选择一个失败，报告应能找到原始输入与证据。真实执行受任务权限约束，不因 procedure 写完就启动设备操作。

交付需求到 Case 到证据的关系、未测范围和剩余风险。结构/Schema/模拟/单元/契约/系统证据分别报告；报告完整可以包含 FAIL，不能为了全绿删除反例或把重跑结果覆盖原失败。
