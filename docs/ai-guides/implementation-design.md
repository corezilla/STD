# ISD AI编写指南

版本：0.2.0-draft.1。主模板：`design.implementation` 0.2.1；对象为软件模块的实现视图。

## 1. 输入与边界

先读[通用 AI 编写指南](../ai-authoring-guide.md)、[ISD规范](../isd-standard.md)和已采用的[模板](../../templates/design/implementation-design.md)。读取实际模块设计、interfaces成员及代码基线，逐项检查实现信息是否已齐全。已齐全就兼作ISD，缺少少量细节就补原章节；不要默认每个模块、每个文件都生成一份文档。

用户要求批量编写时仍逐模块检查；不把旧ISD名称匹配当作对齐完成。文档路径存在也不证明其接口、部署和资源政策现行有效。

先检索模块metadata的implementation_specification.mode，不凭“没有ISD文件”猜测未编写。按规范§2.1登记design_object_id、同对象视图和分卷，parent仍只表示层级。模块决定行为、公共接口、算法规则、不变量、预算和失败；ISD细化精确symbol、私有表示和调用/锁/清理、装配与测试入口。已有实现深度直接embedded，不强迫复制。

先填规范§1的承接矩阵，再展开正文。抽查关键数据、签名、算法、失败和测试是否在模块设计中已经可理解，遇到“ISD再定”先补上游。每项区分原决定、可引用内容、本层新增细化和实现自由度；模块已有全部实现细节就兼作，不重复抄写。阅读[FrameDecoder上游片段→ISD→代码与测试](../examples/isd-frame-decoder/README.md#handoff)，按同一规则ID追到底，并反查代码变化是否需先改上游。

## 2. 专项执行顺序

1. 固定模块ID、直属父对象、模块设计版本和实现范围。只读开篇应知道一次调用解决什么问题。
2. 核实现有文件、构建目标及调用点；区分Current与Target，先列真正的修改差异，不重画整个软件系统。
3. 选一条代表公开调用，先写完整签名和数据定义。逐字段追问来源、所有权、单位、范围和寿命；缺参数时返回权威接口补设计，不由helper凭空合成。
4. 沿入口→校验→算法→输出→释放画图，写关键函数伪代码。以具体输入推演每个判断，明确错误优先级及失败是否留下副作用。
5. 再展开并发、取消、超时、迟到及清理。逐个“等待/完成”指出事实来源和出口，区分状态查询、幂等重放、执行权接管及新业务重试；不把超时当作访问停止。
6. 核算并存资源、启动失败和退出顺序；落到构建、依赖注入、实际hook与测试入口。路径缺失标Planned，关键装配方案缺失是设计缺口。
7. 写V→Case→Vector→独立Oracle和环境/清理。正常结果不能用同一个被测函数反算；没有运行就保持NOT_RUN。
8. 最后更新现有导航、版本/hash和实现映射，按四视角复核，再报告真实完成范围。

## 3. 对每个关键函数的追问

| 追问 | 必须能从正文找到 |
|---|---|
| 谁在什么上下文调用？ | caller、线程/回调、同步/异步、可重入性 |
| 拿到的是完整请求吗？ | 参数与原始字段校验责任；禁止缺字段后声称已校验 |
| 每个分支改变什么？ | 输出、状态、错误优先级、外部副作用 |
| 谁保留输入/输出？ | 借用期限、复制时点、move/释放及失败责任 |
| 多次或并发调用怎么办？ | 去重范围、锁和可见性、取消/迟到、允许与禁止交错 |
| 怎么证明？ | 可执行输入、固定预期和独立证据；设计/实测分开 |
| 安全与诊断在哪里落实？ | 原权限/敏感字段/日志指标规则、检查与脱敏函数、拒绝/上报出口、宿主接收点及Case |

简单函数可分组，重要函数不能只给签名。伪代码集中解释难点，不复制全部实现；内部类/函数保持模块内身份，不申请新的正式模块编号。

## 4. 图例与写法示例

模板就地提供虚构FrameDecoder连续例：§3文件与调用图、§4借用寿命图、§5调用时序、§6算法流程及向量。先阅读这些图，理解图要解释的参数和边界，再替换为项目事实。不能只改标题，也不能用教学例子充当项目已设计内容。

异步模块另外读[异步ExportAgent案例](../examples/module-async-export-example.md)：它不提供等待队列和执行者接管，只演示容量拒绝、同请求重放、受控停止及收口；不要添加案例没有的能力，也不要把异步边界带入同步模块。模板示例没有数据库、线程和外部副作用，不可据此省略实际异步模块的释放证明。

FrameDecoder 的[可编译教学实现](../examples/isd-frame-decoder/README.md)提供完整头文件、私有 helper、调用入口和固定向量。从声明对照字段和分支，再运行构建/测试，不只检查模板中存在函数名。重要算法必须有图、正文和输入推演；C++ 示例尤其核查逐字节大端读取、移位前无符号提升、长度减法和借用视图寿命。

交付时逐项读取模块环境/预算，把各生命周期阶段、总期限、冷/热与并发峰值落实到函数、单调计时点和资源申请/归还；适用 LLM 的能力、上下文、请求量、排队与并发同样映射。不用“由宿主负责”省略宿主入口与组合验证，不以教学运行结果填充未测的产品预算。

每个重要过程都画图，分支对应实际条件，数据交接标类型和ownership。渲染后查看中文、箭头、错误出口和裁切，再对照同一输入。文件树不能代替调用图；成功渲染不能证明流程正确。

## 5. 完成检查与下游承接

- 编码者视角：能否从明确文件、函数和数据开始实现，还是仍需决定公共机制？
- 消费者视角：输入是否足以执行每项校验，接口两端、返回和错误是否一致？
- 生命周期视角：是否有无主内存、重复释放、锁内等待、未知访问被释放或额度重复分配？
- 测试者视角：能否从正常入口建立前置事实，通过依赖边界故障注入制造异常并独立观察，而不直接修改业务终态来伪造流程通过？

对持久化模块追查事务边界、持久提交点与响应点分别在哪个函数，崩溃后哪个入口读取哪条记录、怎样判定已提交并安全恢复。再沿源/目标数据版本核对转换函数、校验/切换点、中断后的继续或回退条件和失败出口；政策来自上游，不由ISD另定。重要恢复与转换过程同样有图、输入推演和异常分支；FrameDecoder无持久状态，不为教学例加数据库。

合法故障注入包括依赖替身、受控故障点、可控时钟及调度，不等于绕过流程。例如经正常调用到达数据库commit边界，分别注入“提交前失败”与“持久提交后响应丢失”，观察恢复入口和原记录；不能直接把任务改成Completed再证明完成路径通过。每次记录注入点、前置事实、故障语义、观察结果及清理/复位；恢复测试的旧数据fixture允许人工构造但须注明来源，不冒充真实生产过程。模拟进程崩溃不能关闭真实崩溃/存储验证，按Case分别记录覆盖和NOT_RUN。

专项检查安全和可观测性：选一个敏感输入/拒绝场景，沿入口到检查点、错误返回或日志/指标逐字段走查；授权服务失败不得默认放行，不能泄露禁止记录的内容，指标沿原ID/单位/窗口，诊断失败不得改变业务结论。只返回结构化错误的库说明宿主收到什么、在哪里接收以及哪些组合测试仍未执行，不虚构库内权限服务或日志平台。

导航检查按[Planned转换例](../examples/isd-planned-mapping.md)对照同一成员的正文和目录：未实现位置仅写计划栏，机器location/symbol为null；用成员ID加role/module/backend定位原行，不能因多一份ISD再增一条实现。已实现先核对文件/声明，再更新原行；保持契约hash及原V/Case，真实Run与教学结果分开。

报告区分作者自审与独立评审，列实际运行检查、未运行项和阻断范围。不要写“目录齐全，因此可以编码”。规格清楚但实现未完成与规格本身缺失必须分别报告。

逐个未决项核对Owner、最晚关闭阶段/截止Gate、分析或决策引用、所需输入、下一步选择判据及关闭条件；允许链接现有问题台账稳定ID，不建立重复台账。责任或期限缺失时指出阻断范围，不能用“待定”占位后宣称关键设计已完成。

交付前核对模板帮助与作者编辑指令没有进入产品正文，图/字段/算法/测试随修改同步。发现接口矛盾回到原权威位置；不要在ISD新增一个“兼容版本”绕过。标准更新不自动迁移项目，实施、提交与发布仍按用户授权。

交付检查使用 `validate-design <完整设计目录> --check-isd-delivery --json`，输入包括模块、ISD、分卷、父链及引用决定。填足十项coverage_mapping，检查适用项落点及条件不适用依据；未执行向量显式填写Actual/Evidence、Verdict和Run为NOT_RUN，不留空也不伪造PASS。空草稿通过基础校验不代表交付；交付检查仅验证关联和槽位，仍逐行核对设计意义、真实输入和Oracle。
