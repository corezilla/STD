# 交付与运维 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`operations.release`、`operations.version-description`、`operations.user-manual`、`operations.installation-deployment`、`operations.operations-manual`、`operations.maintenance`、`operations.bring-up`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

固定实际交付版本、部署环境、配置/依赖、使用者权限、已验证入口、回滚边界和真实故障证据。执行位置必须明确：在哪台主机、哪个目录/终端/接口、由谁对哪个目标操作；不能列一串不知控制对象的命令。

本专项说明如何把已经设计好的能力交给用户、部署者或维护者。若产品没有诊断、复位或回滚能力，返回设计缺口，不能在手册里创造新命令、fallback 或配置路径。

## 2. 专项执行顺序

1. 沿目标读者的一次任务确定开始条件、环境、权限、输入、成功结果与失败出口。
2. 从实际仓库/帮助/接口定义核查命令和配置语义，说明变量来源及禁止误用的目标；示例命令不得假装已在真实环境验证。
3. 对安装、启动、停止、升级、回滚分别检查状态转移和在途数据，说明保留与清除的对象。
4. 设计前置检查、操作、观察、异常处置及复验的可执行步骤；破坏性动作标出影响和既有批准要求。
5. 核查交付版本与证据一致，区分写出 procedure、实际执行和获准发布；不由文档任务自动操作环境。

## 3. 不同模板的实际产物

| Template ID | 核心内容 |
|---|---|
| operations.release | 精确交付物、来源/版本组合、兼容性、验证和发布边界 |
| operations.version-description | 本版本实际变化、已知限制、依赖与升级影响，不混入未来能力 |
| operations.user-manual | 用户任务、入口、输入、可理解结果与错误处理，不是内部模块说明 |
| operations.installation-deployment | 前置条件、完整部署顺序、配置/凭据来源、初始化、冒烟检查及失败恢复 |
| operations.operations-manual | 日常启动/停止、监视、容量与故障处置的执行位置、条件和判定 |
| operations.maintenance | 症状→证据→安全诊断→获准处理→恢复验证，说明不可恢复时的出口 |
| operations.bring-up | 固定硬件/固件/软件基线、预检、仪器/安全边界、分步激活、测量与停机条件 |

启动“进程存在”与“可以接业务”分开；回滚软件版本不保证回滚数据格式；重启成功不保证业务状态一致。写清这些检查依据，不把“如有异常联系管理员”作为全部错误处理。

## 4. 图例与写法示例

步骤简单时用编号清单；升级/恢复涉及多个角色和状态才画流程/时序。拓扑图用于明确操作目标，画出实际主机/服务边界；不要把系统组成图直接当安装步骤。

虚构例：弱写法“重启服务即可恢复”。有效写法先定义允许重启的症状及诊断证据、业务是否停止接收、在途任务如何处理、谁能执行、在哪执行、预期状态转移、失败出口，以及恢复后如何验证业务而非只查进程。

如果已有工具不提供某项必要观察，记录能力缺口并返回系统/模块设计；不要编一个命令或把示意文本包装成可粘贴运行的指令。敏感配置只引用合法获取位置，不把凭据写进文档或日志。

## 5. 完成检查与下游承接

另一位具备规定权限的执行者应知道操作对象、前提、步骤、判据及停止条件；危险操作的失败不能留下无界影响。自动化清理明确哪些测试资产可移除、哪些用户数据必须保留，不用宽泛目录删除作为通用复位方案。

交付说明标明哪些步骤只经文档核对、哪些实际测试过，以及适用版本与环境。操作文档齐全不等于已经发布/部署，文档检查或 release 报告不替代用户与项目的执行授权。
