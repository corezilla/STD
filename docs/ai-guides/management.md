# 工程管理 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`management.project-plan`、`management.tailoring`、`management.development-plan`、`management.semp`、`management.configuration-plan`、`management.risk-plan`、`management.quality-plan`、`management.safety-plan`、`management.security-plan`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

工程管理指南服务九种不同管理计划，不要求一个项目把它们全文互抄。先固定项目目标、生命周期、交付责任、现有流程、资源/里程碑、适用约束、决定权限和实际记录位置；缺失组织责任不能由 Agent 虚构人名、签字或批准。

管理计划规定谁在何时依据什么作决定、保存什么结果。技术设计负责具体机制与参数；计划可以提出约束和证据义务，不能只用“按流程执行”替代它们。

## 2. 专项执行顺序

1. 将项目真实交付物与生命周期列出来，确定哪些管理问题已由既有文档覆盖，哪些需要当前计划承担。
2. 对每项活动明确输入、责任角色、执行时机、产物、退出判据和异常路径，而非只列会议或流程名称。
3. 沿一次正常交付和一次变更/不符合情形走通职责与记录；核查上下游是否互相等待、谁有权接受残余风险。
4. 检查计划的资源、里程碑和验证前提是否相容；依赖不明时形成实际决策问题。
5. 将规则落在现有项目记录位置，区分计划要求、已有执行证据和待建立能力；不要先开发新平台来支撑一份计划。

## 3. 按模板选择管理问题

| Template ID | 必须产出的具体内容 |
|---|---|
| management.project-plan | 目标/成功条件、范围、人员责任、WBS、依赖里程碑、资源与变更方式 |
| management.tailoring | 被裁剪信息项、适用理由、替代承载位置、影响和实际批准依据；不能因为缺资料就免除 |
| management.development-plan | 开发生命周期、实现/集成顺序、工具链、编码与验证活动以及退出条件 |
| management.semp | 需求分配、接口协调、技术预算、模型/分析、技术决策与系统组合验证的责任 |
| management.configuration-plan | 配置项、基线、版本组合、变更控制、构建/交付可追溯与恢复方式 |
| management.risk-plan | 风险识别与评分依据、触发指标、缓解动作、应急处置、残余风险接受责任 |
| management.quality-plan | 过程/产品检查、证据、独立性、不符合处置、纠正措施与关闭判据 |
| management.safety-plan | 危险来源、损害情景、控制及验证责任、残余风险的有权接受方式 |
| management.security-plan | 资产/威胁、信任边界、安全要求分配、验证与漏洞响应、残余风险管理 |

安全计划不能替代硬件/系统安全设计，security plan 不能替代认证授权或升级链的架构说明。风险的“计划采取措施”与“措施执行且有效”分开，不因有人负责就把风险标为关闭。

## 4. 图例与写法示例

角色多且交接复杂时用活动/泳道图；阶段依赖用简短时间线或依赖图；少量责任用表。图中必须区分执行者、决定者和证据接收者，不把每个角色都画成批准者。无需为管理文件套用系统硬件架构图。

虚构例：弱写法“变更须评审，确保质量”。有效计划写明变更提议需绑定哪些配置项及影响分析、由哪些角色核查接口/测试/交付影响、谁有决定权、决定后在哪里冻结基线，以及被拒绝或回退时如何保留可追溯记录。

还须推演紧急修复：既有规则允许什么加急程序，哪些验证不能省略，补证何时完成；没有用户或项目规则支持时不能自行创造紧急豁免。

## 5. 完成检查与下游承接

随机选择一个真实交付物，执行者应知道输入、活动、产物、检查和决定位置；选择一个异常，能找到处置与关闭责任。每项规则有可观察结果，不只列口号或标准名称。

交付计划不等于这些活动已经执行。输出实际采用的流程约束与未定责任，不伪称组织成熟度、认证或审批完成；管理文件要求的技术信息仍需技术文档承担。
