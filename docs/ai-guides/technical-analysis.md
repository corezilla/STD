# 技术分析 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`evaluation.technical-analysis`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

使用 [技术分析模板](../../templates/evaluation/technical-analysis.md)，先确定要支持的具体决定、决定者、可接受条件、固定输入与允许改变的变量。分析不是泛泛技术调研，也不是已批准 ADR；它提供选择依据，采纳由项目决定流程完成。

固定资料、模型/脚本版本、单位、拓扑、配置、负载和来源状态。若实际问题只是在既有方案内选择参数，不扩展成重新选架构；若关键输入缺失，分析可在声明假设下进行，但不能把建议写成产品保证。

## 2. 专项执行顺序

1. 把问题改写成可比较的目标与约束，列硬性排除条件及可权衡项。
2. 选真实可行选项，包括保留现状；只有一项时说明其他项被什么约束排除。
3. 对全部选项使用可比边界与指标，说明计算、仿真、原型或测量方法及误差；不是给每种方案各挑最有利条件。
4. 检查敏感变量、极端负载、失败路径和反例，判断推荐结论在哪些条件下会反转。
5. 写建议、依据、代价、未决项、下一项缩小不确定性的动作及采纳后需要更新的位置。执行实验需单独符合权限。

## 3. 章节怎样产出实际分析

问题与范围章节说明“这次决定什么、不决定什么”；资料和方法说明读者如何复算；选项章节写可行条件而非宣传语；结果章节保留同口径比较和限制；结论章节解释为什么推荐，以及何时需重开选择。

每个数字绑定单位、作用域和证据等级。容量按同一峰值对象组合计算，性能按实际关键路径与并行前提推导；不能把两者互相证明。模型输出保留假设，不用更多小数制造准确感。

资料冲突时先解释版本和测试条件差异；不能平均矛盾数字掩盖问题。复现失败或模型不覆盖的机制必须进入结论限制，而非只藏在附件。

## 4. 图例与写法示例

选项对比常用表，结果变化用曲线/区间图，瓶颈依赖用小图；图标出条件、单位、数据来源和模型/实测身份。只有一个数字时无需图。

虚构例：弱写法“方案 A 内存更大，推荐 A”。有效分析先固定并存对象、公共开销和峰值负载，比较 A/B 的剩余额度与成本/延迟代价，再检查增长或失败回收延迟时是否越界。不能用“容量未溢出”推导吞吐已经达标；性能仍需独立分析或证据。

结论可以是“在假设 H 下推荐 A；若输入上界超过 X 则回到分区选择；下一步核实 H 的数据来源”。真实文档须定义 H/X，不能照抄符号作为已完成分析。

## 5. 完成检查与下游承接

另一位读者应能用固定输入复算关键结论，并知道推荐范围和反转条件。区分作者自查、独立复核和有权者采纳；分析已完成不等于决策已接受。

采纳后把保证和限制写回对应设计/计划，把决定关联 ADR 或项目记录；分析保留推导，不与正式设计分别维护两套预算或协议。
