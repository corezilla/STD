# 评审与决策 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`review.packet`、`decisions.adr`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

评审包先明确请求谁对什么作何种判断，绑定实际被审内容的版本/commit/必要摘要、精确范围、前置决定、证据和未决事项。ADR 先确认这是待选方案还是已有真实决定；普通迁移、成文或格式调整不必虚构一项架构决定。

本专项主入口是 `review.packet` 与 `decisions.adr`。原理图/PCB 的具体技术审查由[硬件专项](hardware.md)承担，通用方法仍适用，但不要求同时建两份主评审材料。

## 2. 专项执行顺序

1. 固定被审输入和请求边界：内容是否已经存在于引用 commit 中，当前 diff 是否超出范围。
2. 对照需求、上级约束和适用规则做实际检查；记录具体位置、问题、影响、建议及证据，不只确认目录齐全。
3. 区分设计未定、实现未完成、证据未获取和材料表达缺陷；修正文档不能自动修好产品。
4. 整理已关闭项与 residual，核实修复后字节及依赖；输入变化时重新确认原 verdict 是否仍适用。
5. 将作者自审、独立 reviewer 结论和有权决定分别保留；没有真实决定就保持待决，不自动终局化。

## 3. 不同模板的实际产物

| 文档 | 应写清的推理 | 完成边界 |
|---|---|---|
| review.packet | 为什么请求本轮评审、实际输入、检查方法/发现、证据、已关闭及剩余问题 | 包可以准备完毕而 verdict 仍待定 |
| decisions.adr | 决策问题、背景约束、真实选项、选择理由、代价、适用条件及重开触发 | Proposed 与实际 Accepted 分开，不代签批准 |

引用的 reviewed/decision commit 必须能证明实际被批准内容，不能早于该内容；修订了协议却还指向旧输入时，不能用“语义一样”口头放行。按项目既有决定 schema 记录字段，不另发明一套批准格式。

多个 reviewer 的局部结论不能自动合成发布批准。消费者确认、技术 Owner、提交许可、canonical promotion、外部发布与 Runtime Activation 的权限边界按既有规则分别处理。

## 4. 图例与写法示例

评审比较适合差异表，决策选项适合权衡表；只有复杂依赖才画影响图，不以架构插画装饰一份决定记录。

虚构例：弱写法“测试通过，建议 ACCEPTED”。有效写法是列出测试覆盖的输入版本、配置及保证，指出内容检查的具体结果、仍未验证的系统组合范围，并把判断限定到本轮请求。例如“可提交候选文档”不能被扩大为“允许生产部署”。

ADR 弱写法“采用方案 A 因其更先进”。有效内容应解释 A 在哪些约束下胜出、放弃 B 的代价、哪些假设会使决定重开。尚未获决定时仍写作者推荐，不改成组织已采纳。

## 5. 完成检查与下游承接

评审者不追查聊天也能定位输入、复现适用检查并理解未关闭事项；实现者能从 ADR 找到不能自行改变的政策及允许的自由度。抽查一个发现和一个关闭项，确认均有实际位置与证据。

报告明确本轮是材料准备、作者自审、独立评审还是实际决定。已有 dirty 或排除路径不能被评审任务顺带提交；归档记录只反映真实动作，不为了目录齐整伪造历史。
