# 子系统与模块 AI 编写指南

版本：0.6.0-draft.1 · 日期：2026-09-13 · 状态：方法草案，待实际写作任务验证

主模板：`design.subsystem`、`design.definition`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

先识别本对象类型、对象 ID 与直属父对象，再选择模板，不能看到“在软件下面”就判为模块。
子系统允许递归：各层仍为 `design_level=subsystem`；`parent_document_id` 指向直属父设计，
不是依赖或目录。根系统直属子系统为一级，每个子系统父子边加一级；缺父、环、跨项目不能推断深度。
正文对象 ID/类型/父对象与父设计组成表、metadata 必须一致，结构检查不能自动证明这种语义一致性。
父设计只展开直属子系统和模块、共同保证及跨边界交互，下级决定自身内部组织；跨层约束显式说明理由与自由度。

新建子系统采用 [design.subsystem](../../templates/design/subsystem-design.md)：先完成子系统整体的概要设计，
软件对象要写出功能、总体方案、软件架构、运行组织及配置/业务处理，不是把模块模板扩大。
共同资源与约束是方案的条件，组合验收是结果；模块与组件用 `design.definition` 深化内部实现。
旧版通用单元模板生成的子系统文档不自动迁移；板卡或 FPGA 本身直接用专项，不重复造子系统文档。

使用 [design.definition](../../templates/design/design-definition.md) 时，先确认单元层级、上级目标与 Constraint ID、分配的预算/行为保证、实际输入输出契约、运行环境、相邻单元和已有实现。系统设计中“交给本模块”不是完整输入；不知道允许修改哪些公共行为时先澄清边界。

硬件或 FPGA 已选专项模板时，直接在专项承接上级约束，不另造一份通用单元文档。本文负责本单元内部如何实现上级要求，不重选产品客户、全系统政策或公共协议。

## 2. 专项执行顺序

对子系统先完成“第 0 层整体方案 → 第 1 层架构与模块概要 → 运行与接口设计”。
只看 §1–5，应能解释软件整体怎样实现主要功能：环境、输入输出、处理原理、模块职责、
进程/线程和通信方式。不能先列所有函数/文件再拼概要，也不能只交约束表让下级决定整体方案。
第 0/1 层是设计观察粒度，不要求软件恰好分为两个层级。下面的步骤贯穿这一过程；
对单个模块则深入本模块实现，不重新进行全子系统架构选择。

1. 把上级约束逐项放到本单元职责、预算与验收位置，标明适用配置和实现自由度。约束不成立时返回上级，不自行降低保证。
2. 选择一个代表输入，明确合法性判断、内部责任、数据变化、结果可见和资源释放，先写完整主路径再补失败/并发。
3. 从过程反推模块分解与实现位置：每个模块必须承担明确行为，说明为什么在这里划分。文件路径是落实位置，不是工作原理。
4. 根据状态与所有权确定数据结构、算法和缓存；再核算峰值资源、竞争、时序及异常退出，避免按代码目录反填职责。
   没有持久化不等于没有状态；内存队列、在途请求、缓冲区、取消及复位仍需权威、Guard 和释放规则。
   只有确实没有相关生命周期时才说明 N/A，不能用“无数据库”跳过此项。
5. 最后形成实现步骤、内部/外部验证及需系统组合验证的保证，回查全部适用功能，不能只验示例主链。

## 3. 章节怎样产出实际设计

子系统模板按 §1 概述、§2 功能与约束、§3 总体方案、§4 软件架构与模块概要、§5 运行设计、
§6 数据状态、§7 接口映射、§8 业务流程与机制、§9 配置、§10 故障安全、§11 调试、
§12 维护升级、§13 部署测试、§14 性能、§15 下游详细设计推进。
功能、模块和业务过程可分别按实际对象扩展子节；概要需解释模块的主要处理与合作，
私有字段、函数内部算法和逐文件实现清单留详细设计。共享数据模型与公共接口仍须在概要阶段确定，
不能以“不写细节”为由推迟关键语义。没有独立升级/运行配置等能力时解释实际边界，不虚构机制。
先贯通一条真实能力，再检查其他能力，不能让模块各写各的后再拼总图。
模块表预留 Document ID、文件名和状态；不存在的文件标 Planned，不当成已接受输入。
新增过程子节按对象扩展，必须说明触发、执行者、条件事实如何产生、结果可见及失败出口；
不为了模板新增队列、服务或恢复机制。单元模板沿其自身章节展开，不套用子系统节号。

| 模板内容 | 作者必须完成的推演 | 交给下游的结果 |
|---|---|---|
| 摘要、功能、上级约束 | 输入条件是否足够，哪项保证由本单元承担 | 能力与约束映射、不可自行改变的政策 |
| 外部接口、内部组成 | 谁调用谁，如何交接，为什么这样拆分 | 唯一契约引用、内部责任和实现位置 |
| 数据、算法、工作过程 | 对象由谁持有，何时读写，如何失败与清理 | 数据生命周期、选择依据及边界行为 |
| 安全、性能、异常 | 未授权/过载/超时下是否仍满足上级保证 | 拒绝、限额、隔离与恢复条件 |
| 实现与测试 | 哪些可独立实现，哪些要协作后才可验证 | 本地用例、系统组合义务与未决项 |

存在 UI/CLI 时给出操作者、执行位置、目标、输入和可观察结果；不拥有这些入口的库不要凭空设计界面。采用已有机器定义时解释必要语义并引用源，不能新抄一份不同的字段表。

## 4. 图例与写法示例

递归对象采用[父子组成 SVG](../../templates/diagrams/subsystem-recursive-composition.svg)和
[同对象运行交互 SVG](../../templates/diagrams/subsystem-recursive-runtime.svg)。虚构 SUB-P 包含 SUB-C（子系统）
和 MOD-D（模块），两图对象 ID/类型/父对象相同；组成图不画调用箭头，运行图才给部署决定及交互方向。
将对象与进程分开：本例两个进程是明确的 Target 选择，不是“子系统必须独立进程”。不得从父图推导 SUB-C 内部线程。

子系统也可复用[逻辑组成 SVG](../../templates/diagrams/subsystem-layered-architecture.svg)：编辑层名和模块，
保留图注中的视图/实现/验证状态及配置范围；图后逐一解释职责、非职责和拆分依据。
这是虚构作业系统分解，不是通用强制架构。它不表达独立进程，不能据此推导调用顺序。

模块层次图可复用[软件分层 SVG](../../templates/diagrams/software-layered-architecture.svg)，左侧层名、模块无图标、仅表示归属；交互另用时序或数据生命周期图。实际文件名和分组编辑入口见[图形目录](../../templates/diagrams/README.md)。不描述未经定制的一般操作系统内部；有自研启动或定制操作系统才展开其责任。

虚构例：弱写法“解析器使用缓存提高性能”。改为先说明缓存保存的是已校验索引还是原始输入、键绑定哪个版本、谁负责失效、并发读取怎样看到一致内容、额度耗尽时拒绝还是逐出；再解释选择代价。本单元额度必须包括在途副本和索引开销，不能只计算有效数据。

不需要把所有缓存都设计成同一种机制；项目未授权新增缓存时，本例仅用于检查既有设计是否说清楚。

依[接口与数据规格映射规范](../interface-data-mapping-standard.md)读取上级成员 ID 与机器来源的实际 version/revision/hash，
逐项记录本单元提供/消费、backend、实际实现文件/symbol 或 NOT_IMPLEMENTED、Constraint/设计 V→Case/环境/Run。
数据类型、寄存器或信号保持原 authority；标准接口核对标准版本及项目绑定，不复制字段再自行修改。
原生硬件/RTL/ABI 用现有工具检查，目录 JSON PASS 不代替电气/时序/互操作。验证计划保留未实现/NOT_RUN/缺测分母，
同一接口的多个 backend 分别检查，单方通过不关闭组合目标。冲突回报原成员 ID、具体输入反例与影响，不能静默换定义。

## 5. 完成检查与下游承接

接口按“系统公共 / 本层直属对象间 / 下级私有”逐项确认唯一维护位置。
本层新增共同协议由本层或其委托的唯一机制/接口文档定义，两端引用；不要全上推或让两端各自定义。
规格缺失是设计缺口，规格完整但代码缺失才是 `NOT_IMPLEMENTED`，分别检查，不能用后者掩盖前者。
验证按被测对象 ID/类型/父对象绑定：SUB-C 局部、SUB-P 直属组合、SYS-EX 系统验证逐级承接，
子级 PASS 不直接推导父级 PASS；每层补充本范围的交互验证及证据。
生成器可用 `--parent-document-id` 保存父链；完整输入再运行
`validate-design <设计目录> --check-design-hierarchy --json`，检查缺父、自指/环、类型和项目边界。
`subsystem_depths` 是从当前完整输入推导的深度，不存成第二套 metadata 层级。旧项目不自动升级或补链。

对子系统先按下表核对项目**已采用**的系统设计，再做组合推演。表中系统章号仅说明当前 STD 模板的
内容位置，不要求升级上级模板或重编系统全文；实际对应使用固定 Document ID/基线及稳定内容 ID。

| 系统设计输入 | 子系统落实位置 | 必须核对的设计结果 |
|---|---|---|
| §3 组件/拓扑、§4 功能、§5 模式与过程 | §2.2、§3–5、§8 | 原身份及外部边界不变，本地新增步骤只是细化，不改变上级可观察顺序 |
| §9 数据流及公共数据模型 | §6.1–6.2、§7 | 核心对象、查找/更新组织、阶段前后形态和类型来源一致；共享不误算复制 |
| §14 信息安全架构 | §10.1 | 身份传播、检查/执行点、凭据及更新信任责任有落实，失效不绕过安全政策 |
| §10.4 调试接口、§11 维护升级 | §11.1、§12.1–12.3 | 原指标/诊断/接口 ID 及口径被继承，控制与撤销有确认，升级不损害数据 |
| §13 可测试性与系统验收 | §13.1–13.4及章内验证表 | 系统设计 V 分解到 Case/环境/Run；隔离、自动化、失败与清理可复现 |
| §12 扩展与兼容 | §14、§14.1 | 共享预算闭合，实例/状态/故障域变化可解释，本地兼容范围不比系统更宽 |

逐条标明“系统已决定 / 本地细化 / 下级自由度 / 差异待决”，不能把“引用了系统文档”当作对齐完成。
数据章节需走一份代表对象的前后变化，不能只演练任务状态。安全检查需演练依赖失效与越权拒绝；
维护检查需解释同名指标在不同组件的范围、窗口及重启口径。条件不适用时说明固定边界，
不为模板新增缓存、调试后门、升级器或扩容机制。
局部与系统组合验证分别反馈；发现矛盾按原 ID 回报原决定方，不静默改接口或放宽约束。

对子系统另做一次“组合检查”：内部预算加共享开销和预留是否落在上级额度内；每个公共规则是否唯一维护；
各模块的局部成功是否真的推出整体保证。将同一代表请求交给所有参与模块逐步推演，再走取消、迟到与资源释放。
任何一步需要猜参数、用无来源的 Guard 或直接修改内部状态才继续，都回到设计修正。
对多个下级文档修改同一约束时，用固定 Constraint ID 回查模块表、接口、图、资源和验证项；
计划路径存在、目录检查通过不证明承接完成，也不授权提交、发布或 Runtime Activation。

选择一条成功、一条失败和一个并发条件，能从入口走到结果与清理，且每项行为有实际责任方。逐项检查上级约束是否分配到内部实现/本地验收；涉及多个单元时另记组合验证，不把本模块单测 PASS 当系统目标关闭。

交付者应能指出实现者可自行选的算法/内部结构与不可改的公共语义。实现路径不存在或测试尚未执行可以如实记录，但共同语义未定不能伪装为“由开发细化”。
