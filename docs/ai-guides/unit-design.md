# 软件子系统与模块 AI 编写指南

版本：0.8.0-draft.1 · 日期：2026-09-13 · 状态：方法草案，待实际写作任务验证

主模板：`design.subsystem`、`design.definition`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

项目采用[软件设计对象编码规范](../software-object-identifiers.md)时，先读取父级对象登记表：
查 S/M 编号、名称、父对象和文档映射，内部模块从所属段追加编号，不按图中位置或文件排序重新编号。
写完核对图文、接口关联和验证对象一致；对象 ID 不填入 `parent_document_id`。

先识别本对象类型、对象 ID 与直属父对象，再选择模板。当前软件链为：总体系统设计 → 软件系统设计 →
软件子系统设计 → 软件模块设计；软件系统可按需直接包含软件模块，不采用递归软件子系统。
`parent_document_id` 指向直属父设计，不是依赖或目录；不计算子系统深度。总体系统与软件系统均为
`design_level=system` 粒度，软件子系统为 `subsystem`，软件模块为 `module`，角色须在正文明确。
对象 ID/类型/父对象与父设计组成表、metadata 必须一致，结构检查不能自动证明领域及业务归属。
软件系统决定直属子系统和模块的协作与共同保证；软件子系统决定内部模块和运行组织；模块深化实现。
必要跨层约束显式说明理由与自由度。软件系统采用 `design.software-system`，由[软件系统专项](software-system.md)指导；不把软件子系统模板上推充当软件系统模板。

新建软件子系统采用 [design.subsystem](../../templates/design/subsystem-design.md)：完成所分配软件范围的概要设计，
写出功能、总体方案、软件架构、运行组织及配置/业务处理，不是把模块模板扩大。
共同资源与约束是方案的条件，组合验收是结果；软件模块用 `design.definition` 深化内部实现。
旧版模板生成的文档不自动迁移；固件系统/FPGA 程序/RTL 模块与硬件系统/板卡/电路单元按专项链承接，
不套用软件子系统层级，不另造一份子系统文档。

使用 [design.definition](../../templates/design/design-definition.md) 时，先确认单元层级、上级目标与 Constraint ID、分配的预算/行为保证、实际输入输出契约、运行环境、相邻单元和已有实现。系统设计中“交给本模块”不是完整输入；不知道允许修改哪些公共行为时先澄清边界。

硬件或 FPGA 已选专项模板时，直接在专项承接上级约束，不另造一份通用单元文档。本文负责本单元内部如何实现上级要求，不重选产品客户、全系统政策或公共协议。

## 2. 专项执行顺序

对子系统先完成“第 0 层整体架构 → 第 1 层分层与模块设计 → 运行与接口设计”。
第2章是第0层，第3章是第1层：仅表示观察粒度，不是运行时层或新增子系统层级。
只读 §1–3，读者应能说明用途与输入、画出整体分层、定位各层模块、解释主要协作，
并找到唯一数据/接口来源及下游设计入口。对单个模块则深入其实现，不套用子系统目录。

1. 读取上位输入，形成 §1：业务、环境、输入输出、功能与需求分别记录，保留约束、基线、
   父对象与验收责任；未知输入反馈上级，不把所有模块或完整架构塞入概述。
2. 贯通代表业务，完成 §2 整体架构图与说明：先确定层或分区、协作方向、公共能力归属，
   再解释原理和取舍。不从模块清单拼总图，不因模板例子强制新增层、服务或队列。
3. 沿相同分区顺序完成 §3：逐层写局部组成图、模块表、各模块处理概要及层内/跨层交接。
   核对架构分区、正式模块、接口角色和实现对象，不用泛化“验证/能力保障”标签代替实现模块。
4. 完成 §4–13 的运行、数据、接口、过程、配置、异常、维护、验证和资源设计。
   用具体输入逐步推演正常/失败/并发、状态事实来源、清理及资源上限；没有持久化仍需设计
   易失状态、配置快照和在途对象的寿命，不能用“无数据库”跳过。
5. 回查整体与逐层设计能否指导下级，在 §14 交付模块设计和验证工作包。共同机制未定先预设计，
   不把“遵循上级”当本地方案，不以个别模块单测通过关闭子系统组合保证。

## 3. 章节怎样产出实际设计

子系统模板为 14 个主章：§1 概述与设计输入、§2 总体架构设计（第0层）、§3 分层与模块设计（第1层）、
§4 运行、§5 数据状态、§6 接口映射、§7 业务流程与机制、§8 配置、§9 故障安全、§10 调试、
§11 维护升级、§12 部署测试、§13 性能、§14 下游详细设计。
功能、模块和业务过程可分别按实际对象扩展子节；概要需解释模块的主要处理与合作，
私有字段、函数内部算法和逐文件实现清单留详细设计。共享数据模型与公共接口仍须在概要阶段确定，
不能以“不写细节”为由推迟关键语义。没有独立升级/运行配置等能力时解释实际边界，不虚构机制。
先贯通一条真实能力，再检查其他能力，不能让模块各写各的后再拼总图。
模块表预留 Document ID、文件名和状态；不存在的文件标 Planned，不当成已接受输入。
新增过程子节按对象扩展，必须说明触发、执行者、条件事实如何产生、结果可见及失败出口；
不为了模板新增队列、服务或恢复机制。单元模板沿其自身章节展开，不套用子系统节号。

| 模板内容 | 作者必须完成的推演 | 交给下游的结果 |
|---|---|---|
| 摘要、功能、上级约束 | 输入条件是否足够，哪项保证由本单元承担 | 能力与约束映射、不可自行改变的政策 |
| 外部接口、内部组成 | 谁调用谁，如何交接，为什么这样拆分 | 唯一契约引用、内部责任和实现位置 |
| 数据、算法、工作过程 | 对象由谁持有，何时读写，如何失败与清理 | 数据生命周期、选择依据及边界行为 |
| 安全、性能、异常 | 未授权/过载/超时下是否仍满足上级保证 | 拒绝、限额、隔离与恢复条件 |
| 实现与测试 | 哪些可独立实现，哪些要协作后才可验证 | 本地用例、系统组合义务与未决项 |

存在 UI/CLI 时给出操作者、执行位置、目标、输入和可观察结果；不拥有这些入口的库不要凭空设计界面。采用已有机器定义时解释必要语义并引用源，不能新抄一份不同的字段表。

## 4. 图例与写法示例

软件系统与直属软件子系统/模块关系采用[父子组成 SVG](../../templates/diagrams/software-design-composition.svg)和
[同对象运行交互 SVG](../../templates/diagrams/software-design-runtime.svg)。虚构 SW-P（软件系统）包含 SUB-C（软件子系统）
和 MOD-D（模块），两图对象 ID/类型/父对象相同；组成图不画调用箭头，运行图才给部署决定及交互方向。
将对象与进程分开：本例两个进程是明确的 Target 选择，不是“子系统必须独立进程”。不得从父图推导 SUB-C 内部线程。

子系统模板 0.6.0 使用同一虚构 EX-JOB/v2 的连续三图，见[图形目录](../../templates/diagrams/README.md#子系统连续三图)：

| 位置 | 图源 | 核对要点 |
|---|---|---|
| §1.2 上下文 | [上下文 SVG](../../templates/diagrams/subsystem-context.svg) | S02 黑盒，业务/管理/执行三个外部对象、输入输出；不表示内部架构 |
| §2 第0层 | [整体架构 SVG](../../templates/diagrams/subsystem-overall-architecture.svg) | 相同 S02 和外部对象，入口/任务编排/执行对接/公共配置四个分区，明确交接及公共服务范围 |
| §3 第1层 | [分层模块 SVG](../../templates/diagrams/subsystem-module-breakdown.svg) | 相同四分区展开 M201–M205，每个模块仍直属 S02；无虚构新父层级 |

上下文图、整体架构图、模块组成图、流程图不可互相替代。组成图可无箭头；架构图需要表达关系时，
用图例区分业务和管理，明确单向/双向含义，不把“无连线”泛化为所有图。分区不是进程、模块或调用栈。
顺序、等待条件与失败分支放 §7 的流程图；§4 的进程部署必须另有设计依据。

SVG 为可编辑源，配套 PNG 为同源导出展示；模板可见图片与源链接同时提供。改 title/desc、
data-object-id/type/parent-id、data-group-id、可见名称、编号和图注后同步导出。保留正式编号，
小字号置于模块名称右侧括号内；分组不自动获得模块编号。按实际正文宽度检查中文、连线、裁切、
对比和层/模块对应。正文解释职责与协作，绘图和排版操作指令只留在本指南及模板帮助中。

模块层次图可复用[软件分层 SVG](../../templates/diagrams/software-layered-architecture.svg)，左侧层名、模块无图标、仅表示归属；交互另用时序或数据生命周期图。实际文件名和分组编辑入口见[图形目录](../../templates/diagrams/README.md)。不描述未经定制的一般操作系统内部；有自研启动或定制操作系统才展开其责任。

虚构例：弱写法“解析器使用缓存提高性能”。改为先说明缓存保存的是已校验索引还是原始输入、键绑定哪个版本、谁负责失效、并发读取怎样看到一致内容、额度耗尽时拒绝还是逐出；再解释选择代价。本单元额度必须包括在途副本和索引开销，不能只计算有效数据。

不需要把所有缓存都设计成同一种机制；项目未授权新增缓存时，本例仅用于检查既有设计是否说清楚。

依[接口与数据规格映射规范](../interface-data-mapping-standard.md)读取上级成员 ID 与机器来源的实际 version/revision/hash，
逐项记录本单元提供/消费、backend、实际实现文件/symbol 或 NOT_IMPLEMENTED、Constraint/设计 V→Case/环境/Run。
数据类型、寄存器或信号保持原 authority；标准接口核对标准版本及项目绑定，不复制字段再自行修改。
原生硬件/RTL/ABI 用现有工具检查，目录 JSON PASS 不代替电气/时序/互操作。验证计划保留未实现/NOT_RUN/缺测分母，
同一接口的多个 backend 分别检查，单方通过不关闭组合目标。冲突回报原成员 ID、具体输入反例与影响，不能静默换定义。

## 5. 完成检查与下游承接

接口按“系统公共 / 本层直属对象间 / 下级私有”逐项确认唯一维护位置。
本层新增共同协议由本层或其委托的唯一机制/接口文档定义，两端引用；不要全上推或让两端各自定义。
规格缺失是设计缺口，规格完整但代码缺失才是 `NOT_IMPLEMENTED`，分别检查，不能用后者掩盖前者。
验证按被测对象 ID/类型/父对象绑定：SUB-C 局部、SW-P 软件系统直属组合、SYS-EX 总体系统验证逐级承接，
子级 PASS 不直接推导父级 PASS；每层补充本范围的交互验证及证据。
生成器可用 `--parent-document-id` 保存父链；完整输入再运行
`validate-design <设计目录> --check-design-hierarchy --json`，检查缺父、自指/环、类型和项目边界。
检查输出 `design_parent_links`，不输出子系统深度；子系统父对象不能再是子系统。该结构检查不能凭 system 枚举证明软件系统角色，须复核正文。旧项目不自动升级或补链。

对子系统先核对直属软件系统设计的分配，再沿其引用追溯项目**已采用**的总体系统约束，不绕过软件系统重新分配预算。
下表用于核对继承的总体约束，再做本地组合推演。表中系统章号仅说明当前 STD 模板的
内容位置，不要求升级上级模板或重编系统全文；实际对应使用固定 Document ID/基线及稳定内容 ID。

| 系统设计输入 | 子系统落实位置 | 必须核对的设计结果 |
|---|---|---|
| §3 组件/拓扑、§4 功能、§5 模式与过程 | §1.6、§2–4、§7 | 原身份及外部边界不变，本地新增步骤只是细化，不改变上级可观察顺序 |
| §9 数据流及公共数据模型 | §5.1–5.2、§6 | 核心对象、查找/更新组织、阶段前后形态和类型来源一致；共享不误算复制 |
| §14 信息安全架构 | §9.1 | 身份传播、检查/执行点、凭据及更新信任责任有落实，失效不绕过安全政策 |
| §10.4 调试接口、§11 维护升级 | §10.1、§11.1–11.3 | 原指标/诊断/接口 ID 及口径被继承，控制与撤销有确认，升级不损害数据 |
| §13 可测试性与系统验收 | §12.1–12.5及章内验证表 | 系统设计 V 分解到 Case/环境/Run；隔离、自动化、失败与清理可复现 |
| §12 扩展与兼容 | §13、§13.1 | 共享预算闭合，实例/状态/故障域变化可解释，本地兼容范围不比系统更宽 |

逐条标明“系统已决定 / 本地细化 / 下级自由度 / 差异待决”，不能把“引用了系统文档”当作对齐完成。
数据章节需走一份代表对象的前后变化，不能只演练任务状态。安全检查需演练依赖失效与越权拒绝；
维护检查需解释同名指标在不同组件的范围、窗口及重启口径。条件不适用时说明固定边界，
不为模板新增缓存、调试后门、升级器或扩容机制。
局部与系统组合验证分别反馈；发现矛盾按原 ID 回报原决定方，不静默改接口或放宽约束。

对子系统先做“三图一致性检查”：C1 与 A1 的边界及外部对象相同，A1 每个分区在 M1 有对应展开；
模块表中的正式对象均能定位到分区和唯一父对象，跨层交接回链接口及验证责任。分区无对应、
新增无来源模块或用部署图冒充架构时，必须回到正文修正，不能只检查有图、有表。

对子系统另做一次“组合检查”：内部预算加共享开销和预留是否落在上级额度内；每个公共规则是否唯一维护；
各模块的局部成功是否真的推出整体保证。将同一代表请求交给所有参与模块逐步推演，再走取消、迟到与资源释放。
任何一步需要猜参数、用无来源的 Guard 或直接修改内部状态才继续，都回到设计修正。
对多个下级文档修改同一约束时，用固定 Constraint ID 回查模块表、接口、图、资源和验证项；
计划路径存在、目录检查通过不证明承接完成，也不授权提交、发布或 Runtime Activation。

选择一条成功、一条失败和一个并发条件，能从入口走到结果与清理，且每项行为有实际责任方。逐项检查上级约束是否分配到内部实现/本地验收；涉及多个单元时另记组合验证，不把本模块单测 PASS 当系统目标关闭。

交付者应能指出实现者可自行选的算法/内部结构与不可改的公共语义。实现路径不存在或测试尚未执行可以如实记录，但共同语义未定不能伪装为“由开发细化”。
