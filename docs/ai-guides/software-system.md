# 软件系统设计 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-13 · 状态：方法草案，待实际项目试写验证

主模板：`design.software-system`，独立版本 `0.1.0`。先读[通用 AI 编写指南](../ai-authoring-guide.md)，
再读项目已采用的[软件系统模板](../../templates/design/software-system-design.md)及其全部编写建议。
本指南从总体系统设计的产品先行、预设计、过程推演与下游承接方法派生，不要求通读总体模板的硬件专业章。
本次只使用 STD 已有通用材料和虚构案例，不依赖或读取保密 demo；教学内容不代表项目设计决定。

## 1. 输入与边界

先确定本文的位置，而不是先填父文档字段：

| 使用位置 | 实际输入 | 必须承担的责任 |
|---|---|---|
| 纯软件项目顶层 | 已采用需求、客户场景、环境及现有代码/契约 | 从产品用途到整体软件架构与验收；没有父设计时 parent_document_id 可为空 |
| 总体系统的软件领域设计 | 总体设计的固定 Document ID/版本/commit、软件职责、Constraint、公共机制与接口 | 细化软件整体，不重决总体预算及跨软硬件保证；parent_document_id 指向真实父设计 |

两种位置均为 `design_level=system`，默认 `domain=software`；它们是同一模板的适用模式，不新增
metadata 枚举。纯软件项目不强制再建一份重复的总体设计。存在硬件依赖只说明资源、协议和失效
边界，不展开板卡或 FPGA 内部实现；普通操作系统不是软件架构的自研组成，定制/改造时才展开。

取得输入后实际打开内容，区分事实、批准决定、假设和未决项。代码已存在不证明与文档一致；
规格未定义是设计缺口，规格完整但代码没有实现才是 NOT_IMPLEMENTED。用户没有要求时不主动
检查模板是否更新，不更新项目 lock，不把编写任务推导为发布或 Runtime Activation 授权。

## 2. 专项执行顺序

1. **产品与范围**：先形成 §1–2，选一项客户业务任务，解释输入、处理和结果。只有维护操作
   或技术组件名时先补真实用途；无 UI 的库、工具、API 仍应写清使用流程。
2. **整体方案**：简短承接业务场景，在 §3.1 先展示软件系统架构图，§3.2 逐组件解释职责，
   再说明取舍、约束及机制。§4 展开功能，§5 展开直属对象概要，不另建全系统总图。发现机制、取舍或验证
   说不清时，做“问题/约束 → 选项 → 正常与失败推演 → 推荐与代价 → 未决项”的预设计，
   选定后写回正文，不把登记 PENDING 当完成。独立部分可以继续，不能凭空补产品能力。
3. **运行与一条完整路径**：形成 §6 运行部署和 §7 代表业务，同时确定 §8 状态及 §9 交接。
   从一个具体输入逐步核对执行者、身份、读写、确认、结果可见和清理；没有运行时统筹者时
   不能用工程 Owner 填空。正常走通后再演练拒绝、并发、失联、取消和重启。
4. **覆盖其他能力**：建立能力→对象→过程→接口→验证的矩阵，所有实际能力进入分母。
   不让一个成功案例掩盖未设计入口；新事实改变公共规则时回查状态表、接口、图、资源和用例。
5. **横向工程设计**：完成 §10 配置、§11 维护、§12 性能、§14 安全和 §15 构建交付。
   从已选方案推导控制、观测、预算和兼容，而不是罗列“高可用、自动化、可扩展”。
6. **验证与分工**：用 §13 确定测试方法、部署复位、并发隔离及自动化；在 §16–17 把固定输入、
   自由度和组合义务交给下级。接口语义/错误/测试向量评审后可并行实现，两端实现测试通过再集成。
7. **回写与复审**：回写开篇与概览，删除重复协议，把控制记录放文末。折叠帮助后按新读者视角
   通读正文；格式和目录 PASS 只是结构证据，不能代替设计质量或运行验证。

局部修订只检查变化及直接依赖，不重跑完整写作流程。工作记录可留在项目已有位置，
不要求为每节建立新文件，也不擅自新增队列、配置路径、selector、重试或高可用机制。

## 3. 章节怎样产出实际设计

| 模板位置 | 必须解决的问题 | 可检查的设计输出 |
|---|---|---|
| §1–2 位置与产品 | 谁使用、解决什么、承担哪些目标 | 范围、场景与可观察成功条件 |
| §3 系统概览 | 系统由什么组成、如何分工，原理和取舍是否成立 | §3.1 架构图、§3.2 职责与 S/M 对象总表、取舍、约束分配、机制/文档映射 |
| §4 功能与交互 | 全部正式入口做什么 | 能力总表、行为原理、页面/CLI/API 反馈 |
| §5 对象概要 | 各组成如何履行已分配的职责与约束 | 引用 §3.2 对象 ID，展开子系统及直属模块的输入、处理、协作与失败行为 |
| §6 运行部署 | 在哪里、什么上下文执行和通信 | 对象到进程/实例/节点映射、等待和故障域 |
| §7 重要过程 | 从操作到结果怎样完成与失败 | 启动、业务、配置、停止/恢复的完整阶段 |
| §8 数据 | 谁维护事实，何时提交和释放 | 数据流、状态所有权、持久化/缓存与寿命 |
| §9 接口 | 双方是否能按契约实际调用 | 完整机器映射、请求响应、错误与兼容 |
| §10 配置 | 输入怎样得到唯一生效行为 | 来源优先级、校验、作用域、切换与确认 |
| §11 维护 | 如何发现、定位、诊断和恢复 | 指标/日志、自检路径、升级与回滚保证 |
| §12 性能 | 各局部组合能否满足上限 | 负载、峰值、预算、瓶颈和扩展边界 |
| §13 测试 | 如何产生输入并独立判定 | 方法/Oracle、环境复位、并行隔离、Case/Run |
| §14 安全 | 哪些输入、身份和更新不可信 | 检查/执行/撤销点及威胁验证 |
| §15–17 交付与承接 | 怎样构建、实现、集成并关闭目标 | 可追溯制品、依赖计划、下级输入和组合验收 |

§3 先展示架构并逐组件解释职责和整体原理，§5 展开对象概要，§6 讲运行载体，§7 讲过程，§8 讲对象形态与生命周期。
这些视角互相引用，不维护五份相同流程。完整公共接口唯一在契约维护，正文解释原理和边界。
章节可按真实能力扩展子节，不以模板例子的“转换服务”强制项目采用作业、队列或进程模型。

## 4. 图例与写法示例

软件架构优先复用可编辑 SVG，不用为每个模块构造图标。场景图表达逻辑应用环境，不必写实。
全系统架构图放在模板 §3.1 正文开头，后接 §3.2 各组件职责，不等功能与对象概要写完才展示。
对象总表在 §3.2 唯一维护；§5 如需局部图只展开相应对象边界，§6 的运行部署图保留独立视角。
每图注明 Current/Target/Transitional、适用版本/配置，能力实现状态与验证状态分开；图中未来部分
用不同样式及文字标明，不能通过相同颜色把计划能力画成已实现。

| 问题 | 图形入口 | 必须修改和核对 |
|---|---|---|
| 系统包含哪些对象 | [软件直属组成 SVG](../../templates/diagrams/software-design-composition.svg) | 层次、对象/父对象 ID、类型、图后职责；不加调用箭头 |
| 左侧层名、内部模块布局 | [软件分层 SVG](../../templates/diagrams/software-layered-architecture.svg) | 层名与模块名、底色对比、无图标无连接线；只保留实际定制系统层 |
| 同一对象如何运行和交接 | [软件运行交互 SVG](../../templates/diagrams/software-design-runtime.svg) | 承载进程/实例、箭头方向、交接语义与接口 ID；不从组成图猜进程 |
| 需要详细时序或状态 | [机制图形目录](../../templates/diagrams/mechanism/README.md) | 选择与问题对应的图，不机械画全套；引用唯一协议的事实来源与 Guard |

复制 SVG 时同时改 title/desc、可见文字、data-object-id/data-object-type/data-parent-id 和图注。
采用[对象编码规范](../software-object-identifiers.md)时，将虚构 SW-P/SUB-C/MOD-D 替换为本项目
登记的身份；对象 ID、Document ID 和机制 ID 不混用。增减块后调整坐标/viewBox，在 Markdown
实际渲染检查文字遮挡、裁切、对比与缩放可读性。保存可编辑源；图片不能成为第二套设计 authority。

**虚构完整主线示例**：文档转换应用先验证输入与访问权限，再在已有额度内转换，核对输出后
发布可取得的结果。配置模块提供固定版本规则，处理子系统完成转换，两者的共同交接由软件系统决定。
它可采用单进程，也可选择隔离进程；多进程只是要经负载、安全与恢复分析支持的方案，不是模板要求。

| 弱写法 | 为什么不足 | 应当设计的内容 |
|---|---|---|
| 使用异步提高性能 | 没有调度、等待和失败归属 | 明确执行上下文、在途上限、确认、取消和退出；再以负载证明收益 |
| 返回失败后重试 | 超时可能只是调用方未知 | 按原身份查询结果，确认旧执行者停止/隔离和副作用条件后才决定重试 |
| 数据库保存任务 | 没有权威和提交保证 | 明确写入者、提交点、回复条件、崩溃恢复和保留期限 |
| 系统可自动部署 | 没有已知初始状态 | 写从依赖准备到业务就绪的入口、版本和检查，再说明安全复位范围 |

例子只演示“怎样把问题设计清楚”。没有持久任务的只读工具不应照搬任务状态、取证或写隔离。

## 5. 完成检查与下游承接

第一轮只读开篇：新读者能否说出用途、使用场景、输入处理输出、分工及范围？第二轮逐能力带
具体输入推演：遇到“接收方无法确定对象、字段或下一步”就回到设计，不靠作者口头补充。

重点追查每个条件的事实来源。例如“停止完成”“取证不可恢复”“配置已生效”由谁、检查哪些
记录、在什么期限后得出？每个等待都要有合法出口。对有副作用且涉及取证与资源收口的机制，
演练“证据无法恢复但已安全停止”；只读路径检查中断、迟到响应和临时资源，不凭空增加状态。

依[接口映射规范](../interface-data-mapping-standard.md)，核对正文版本/封面/metadata/目录、
角色、源签名、完整性及唯一机器定义。目录中的 request/response 角色必须与源对应，缺项不能
仅靠 schema-valid 放行。设计未定义、代码未实现、没有运行记录分别列入覆盖，全部必需消费者
各有验收义务；一个 backend 或模拟端通过不能关闭整个软件系统目标。

下级交付由 §3.2 登记对象、§3.4 分配约束，§5.1 展开概要，§17.1 固定下级文档与验收任务；软件子系统使用 `design.subsystem`，
软件模块使用 `design.definition`。软件系统可直属模块，软件子系统不递归。子系统局部测试、
软件系统组合测试，以及适用时的总体系统测试，绑定不同被测对象与实际 Run，不能混称“集成已通过”。

完成前核对 §7 过程、§8 状态、§9 接口、§10 配置、§11 维护、§12 预算与 §13 验证是否引用同一
套规则；修改公共语义后记录仍保留旧语义的位置并修正。每节必须回答实际决定、依据、下游约束、
自由度和检查办法，不能让表格完整性掩盖关键机制未定。

## 6. 生成与结构检查

纯软件项目可按已有项目路径策略生成；默认输出 `docs/20_system_design`。例如：

```bash
./scripts/new-design --project example --template design.software-system \
  --name example-software-system --title '示例软件系统设计说明书' \
  --project-root /path/to/project --repository example/repo \
  --owner software-owner --author author
```

领域模式增加 `--parent-document-id` 指向真实父设计 Document ID。生成器保留编写建议，移除
明确标记的 STD 教学图和派生说明；它不会替项目作设计、创造上级输入或批准状态。
`validate-design <设计目录> --check-design-hierarchy --json` 可检查完整输入中的父链；
纯软件根无需虚构父节点。它不证明角色的业务真实性，不代替上述内容复审，也不验证运行性能。

初版应在真实项目中试写并记录返工原因，再修改对应建议；本模板和指南尚未因此声称通过实际设计验收。
