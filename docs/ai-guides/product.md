# 产品与交付定义 AI 编写指南

版本：0.1.0-draft.1 · 日期：2026-09-11 · 状态：方法草案，待实际写作任务验证

主模板：`product.solution-definition`、`product.sku-specification`、`product.roadmap`。
先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的对应模板。本文补充本类型的工作方法，不重复公共来源、权限和状态规则，不自动升级项目模板。

## 1. 输入与边界

先取得已明确的客户类别、实际使用者、业务任务、部署/维护条件、产品边界、交付内容和工程证据。研发 Owner 不是客户，维护操作不能代替主要业务场景，未来目标不能混入当前 SKU 承诺。

本指南区分解决方案、SKU 和路线图。它们消费系统能力与验证结论，但不能反过来把营销文字当实现证明；未确认的价格、上市时间、支持上限或外部能力不得推测成事实。

## 2. 专项执行顺序

1. 为每类主要客户写一次完整任务：原问题、如何使用、谁提供环境、何为成功、哪些条件不适用。
2. 从任务推导必须交付的软硬件/服务/文档/配置及责任，区分本产品与客户设施或外部系统。
3. 将能力映射到已确认配置和证据，确定支持范围、限制、组合及依赖；无法证明的指标保留为目标。
4. 比较变体或阶段时统一口径，检查一个能力变化如何影响容量、隔离、部署和维护。
5. 写明确的交付/验收边界及未决产品决定，交给设计、交付与验证责任方，不凭文档措辞关闭工程缺口。

## 3. 不同模板的实际产物

| Template ID | 主要问题 | 输出边界 |
|---|---|---|
| product.solution-definition | 给谁解决什么问题，在什么环境组合哪些能力 | 使用/部署方案、价值到技术约束的推导、责任和限制 |
| product.sku-specification | 实际交付哪一种配置、包含什么、支持什么 | 精确变体、软硬件/许可/配置、条件化能力与验收 |
| product.roadmap | 当前、已承诺与规划阶段分别交付什么，依赖什么 | 阶段目标、依据、依赖、不确定性与进入条件 |

SKU 中同名指标要有同一单位、负载、版本和拓扑；原始资源量不是可支持业务量。路线图区分已批准承诺和 Proposed，不把估算时间表达为确定交付日期；风险应影响进入条件而非只是脚注。

## 4. 图例与写法示例

应用图采用[逻辑场景样式](../../templates/diagrams/README.md)，突出用户、业务对象、产品和环境的关系；不要求真实场地摄影或写实人物。变体比较用表，阶段依赖用时间线，产品图不能替代工程连接定义。

虚构例：弱写法“适合企业，支持大规模部署”。有效描述分别写单站点断网使用者与集中多租户使用者的任务、接入和维护条件，再指出差异对升级、隔离、容量和恢复的要求。是否销售给两者、哪个优先，仍由产品决定，不由示例决定。

对“支持 N 个任务”，必须有任务类型、并发口径、输入规模、配置和验证状态；若只是算术边界应明确标注，不能变成 SKU 支持承诺。

## 5. 完成检查与下游承接

只读开篇能回答给谁用、怎么用、解决什么问题和在哪里运行。每项产品承诺可追溯到工程输入/证据及适用条件，每项依赖有提供方；SKU 组合不能拼接互不兼容的最好指标。

交给系统设计的是业务约束与成功条件，交给交付/验收的是明确范围和判据。证据缺失与产品选择未定分别处理，文档成文不授权销售发布或运行上线。
