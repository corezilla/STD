# 系统机制 AI 编写指南

版本：0.2.0-draft.2 · 日期：2026-09-12 · 状态：方法草案，待实际写作任务验证

主模板：`design.system-mechanism`。先读[通用 AI 编写指南](../ai-authoring-guide.md)，再读项目已采用的[机制模板](../../templates/design/system-mechanism-design.md)。本文从系统指南 `0.4.0-draft.2` 的机制入口独立；本轮对应模板 `1.5.1` 工作稿，补实取证条件的事实来源和异常演练适用性，不改变项目采用或产品机制。

## 1. 输入与边界

至少取得上级系统的实际基线、机制目标/约束、已有提供与消费方设计、公共操作与对象定义、适用拓扑和失败假设。找到路径后要打开内容；不把局部实现或旧协议自动升级为共同规则。一个 Owner 管多个单元，仍可能有跨运行职责的协议；多个作者写同一模块，也不自动构成系统机制。

系统正文保留端到端原理、关键阶段、系统约束和代表失败，机制正文唯一维护详细交互与状态，不在两处维护相同流程细则。硬件专用时序等只在确有依赖时引用专项，不要求写一遍整机设计。

## 2. 专项执行顺序

收到 `design.system-mechanism` 任务时，Agent 沿机制模板的 15 章主线使用以下执行顺序。系统指南的产品/硬件专业章是完整系统的写作方法，不要求每份机制另写客户全景、整机选型或下级 RTL；适用内容以机制
模板附录 A 和实际系统约束为准。工程 Owner 的人数不决定是否跨单元，独立运行职责和共同
协议才是边界；已有完整机制文档只维护唯一来源，不为模板重新建一套。

1. **固定输入与能力范围**：读已采用系统基线、Process/Step/Constraint ID、实际公共契约及
   提供/消费方已有设计。先写一页机制概览：为谁解决什么协作问题、在哪里运行、如何处理输入、
   输出意味着什么、为什么选择这种分工。不要把系统摘要复制成机制正文，也不能只列链接。
2. **逐能力建立设计工作包**：不是选一条主链就宣告全覆盖。列实际入口、模式及其双方承接，
   按四类实际缺口区分共同方案未定、已有局部定义待整合、旧契约冲突、完整设计待实现。
   先打开固定来源的实际字段/行为定义，再判断完整性；不同协议版本或历史描述冲突需裁决，
   不能靠新增空表消除。仅阻塞受影响依赖，独立部分可继续。
3. **先设计，再写图和段落**：对说不清的机制做简短预设计，列输入/约束、可行选项、正常与
   失败推演、推荐方案与代价，再回写选定的流程/协议。只有作者真正决定了什么，才能写成正文；
   “由下游实现”不能替代共同语义。不要为补齐目录引入通用控制服务、Queue、lease 或配置路径。
4. **按问题选择图**：使用下表的已有 SVG 源，不让 ImageGen 猜协议或拿系统分层组成图代替时序。
   每图只解释一类关系，正文紧随图说明代表输入、关键判断、结果与取舍；完整字段仍唯一维护。
   没有复杂状态转换的只读机制可用短表，不要求六图全画。任何简化要保留关键边界和未画内容。
5. **落实通用设计问题**：沿实际拓扑核查目标身份与共享故障域；沿对象核查局部/全局一致性、
   volatile/durable 边界与资源释放；沿操作核查准入、确认、超时、旧执行与重试；沿维护/验证
   核查完整命令、自检路径、统计口径、注入命中、并发隔离和自动化清理。按实际条件展开，
   不把不存在的硬件或持久化强塞进软件只读机制。
6. **形成下游输入及组合验收**：每项能力关联全部提供方/消费者、固定共同保证、内部自由度、
   本地与组合验证责任。接口语义、错误和测试向量评审后可并行实现；各方契约验证后集成，
   组合验证后才关闭目标。未实现与 NOT_RUN 如实记录，不伪造签收、执行或上线授权。

**这些图如何复用**：先读[机制图形说明](../../templates/diagrams/mechanism/README.md)。复制所需 SVG
到项目自己的文档资产目录，修改 `title`/`desc`、对象名称、分组 ID、基线/状态、连线端点和图例，
并按真实事实替换图后解释；名称相同而语义不同也必须改。不要仅换项目标题、保留 EX-OBS 参数。
图形沿用灰蓝文字模块和单独测试控制色；当前/目标状态另用文字及边框，不暗借颜色。布局超出
正常阅读宽度时分图或换行，不无限缩小字。SVG 是维护源，PNG 是本地渲染导出，修改源后同步
导出并在约 900 px 正文宽度检查中文、箭头、遮挡和图注；不得把密集图直接当已通过渲染检查。
资产复制到项目后引用项目路径，不依赖本机 STD 绝对路径；STD 生成器会删除教学图文块，
Agent 仍须填入真正的设计图和正文，不能将生成空架子当成设计完成。

**共用案例与事实边界**：原六幅关系图及用途图解释[系统指南 §8.8](../ai-system-design-authoring-guide.md#88-完整小例两个单元的只读版本核对) 的 EX-OBS-01/v1，不是多份新协议。该定义是
本案例唯一公共契约；图中省略完整字段、错误表与 CLI 规则时回查原文，发现矛盾先改图而不
擅自改协议。它刻意选择只读、无历史存储、无自动重试，不为写操作提供安全接管范本。
测试图的延迟夹具是拟议测试环境能力，尚未实现/验证，不是生产端新增故障接口。主流程、
部分结果、进程退出与资源期限需要一起读，不能用“只读”省略资源清理。

新增两幅有副作用图唯一参照[暂存导出完整案例](../examples/mechanism-side-effect-example.md) EX-EXPORT-01/v1。
先读其范围和全部接口实例，再看图；不能把私有临时文件可丢弃的前提套到外部业务写入。

## 4. 写法示例：失联不是失败证明

以下为虚构方法例，不是新增协议。弱写法：“Worker 超时后自动重试，保证最终完成。”它没有证明旧执行是否终止，也没有给重复副作用设边界。

有效设计先区分“结果未知”与“确认未执行”，说明读取哪个权威状态、谁能撤销旧写权限、撤销何时生效，以及幂等/去重依据。只有确认旧执行者停止或被隔离且满足重复执行条件，才允许新执行；无法证明时保持阻塞或转人工。任务身份与执行代次由唯一契约定义，不能在示例里默认“新 lease/同 generation”就安全。

若选择只读 EX-OBS 教学路径，则新采样只产生新观测上下文，不是恢复旧写操作；也仍须有目标核对、迟到结果隔离和有界资源清理。把这种差异写进操作语义、失败路径和测试判据，不能只在风险清单加一句提醒。

## 5. 完成检查与下游承接

第一轮先扮演新读者，只看开篇，不看职责表与协议：能否说清什么时候用、解决什么问题、处理范围和得到什么结果？
记下实际复述及误解点，再改开篇；“有一页摘要、有图”不是验收。作者模拟此步骤只算自审，独立阅读验证需真实另一位读者。

折叠全部帮助、移除教学块后，让读者按真实输入解释用途和执行链；
再逐项对照六种关系（可由图、表或正文承载），核对相同 Operation/Object/State/Constraint ID，
尤其检查确认不等于生效、局部成功不等于组合成功、本地释放不等于远端已停。对全部适用能力
走查正常、部分失败、退出/迟到、并发/过载、配置交叠及清理；对有副作用的机制另核对旧写入
强制失效和去重依据。最后确认下游约束、自由度及本地/组合验收闭合。结构/链接/渲染检查、
作者自审和另一位读者的独立理解验证分别报告；未实际开展独立评审就写未做，不自行宣布通过。

## 6. 双方调用演练：用具体输入找设计缺口

先选择场景和冻结实例，填出一套完整请求/响应，包括失败返回；沿同一 operation/对象从准备走到释放。
逐步写“调用方现在知道什么→完整输入→接收方如何定位及校验→实际动作/确认→调用方下一步”。
如果其中一步还要靠口头补目标、版本、字段或错误含义，停止填空，回到设计补齐公共语义。
这里的双方演练是角色视角检查，不自动授权创建协作 Agent 或运行服务。

对每个关键条件追查“这个事实如何产生”：谁在什么事件后写入哪个权威记录，什么动作/观察能证明它，
何时固定、何时可能迟到或失效，谁消费；不能只写“已确认”“准备完成”“取证结束”。沿条件倒查到实际生产者，
若所有参与方都在等别人产生事实，或者只有测试直接赋状态才能前进，属于设计缺口，不是用例补一行赋值即可关闭。
对事实不存在、无效、无法读取分别推演；以真实输入/事件或具名故障注入触发判定，断言由被测逻辑生成。

用[案例 §4](../examples/mechanism-side-effect-example.md#4-完整调用契约)演练：同 ID 不同 payload、旧 agent_instance、串错 request_id、
合法单字段但非法组合、重复 execute、丢失响应、finalize 前提不足。逐例指出错误后仍可调用什么；
不得假设“错误无副作用”或改一个 request_id 就能安全重新执行。客户端只验证 JSON 类型还不够，须核对对象关联及跨字段状态。

## 7. 每个异常的五轴与等待检查

每个异常按实际语义核对以下判断，不用单个 done/failed 概括。判断不同步并不必然矛盾，须由实际契约解释；
不适用项注明条件和理由，不为填表创建五套不存在的状态或服务：

| 检查轴 | 必答问题 | 证据不足时的处理 |
|---|---|---|
| 结果已知性 | 到底未受理、已成功/失败，还是未知？由谁证明？ | 不把通信失败改写为业务失败 |
| 访问安全 | 旧执行是否仍能访问或产生副作用？谁强制隔离、排空？ | 不由超时/调度标签推断安全 |
| 操作终态 | 本操作选择什么终态，还允许什么调用？ | 允许契约定义的未知结果封结，不伪造成功 |
| 资源释放 | 哪些对象已归还，哪些隔离，哪些证据/防重放记录仍保留？ | 不用本地返回代替远端释放证明 |
| 重新准入 | 新任务与旧操作重试的前提分别是什么？ | 资源空闲不代表重执行权限或外部补偿完成 |

**适用条件**：同时涉及业务副作用、取证封结和资源收口的机制，必须补一条“证据无法恢复但已安全停止”
的演练和验证项，例如案例 EX-T3。安全可独立证明时检查能否合法封结 UNKNOWN、清理并接受显式新任务；
若契约不支持这种收口，应说明剩余风险与合法阻塞出口，不为通过演练临时新增机制。
安全仍未知时保持隔离/阻塞；凭据丢失本身不能成为伪造成功或盲目重试的理由。
真正只读、没有写入隔离和取证封结状态的机制，改查调用中断、迟到响应和临时资源释放，
并核对重新采样与原调用的边界；无需照搬 EX-EXPORT 的 stop/collect/finalize 或新增取证服务。

有取证步骤时，按[完整案例的取证转换表](../examples/mechanism-side-effect-example.md#42-操作失败与后续动作)
核对唯一来源、来源如何封闭、可采信凭据条件、期限、封结动作与审计。
来源已封闭且确认为空，与无法读取该来源是两回事；超时不能直接生成 UNRECOVERABLE。
执行中取消必须能从调用入口推演到规定终态或有依据的阻塞，不靠直接修改内部 evidence/receipt 枚举放行。

另把主路径、取消、回退的依赖写成带适用条件的图或短表：对每个等待列出等待者、事件生产者、资源占用、期限和合法出口。
检查 stop 是否等待 collect、collect 是否反等 stop；release 是否等一个未选分支；撤销 Worker 写权是否误封 C 的取证/回退权。
AND 与选定分支 OR 分开。正常路径能终结不说明取消也能终结，清理阶段不可提前销毁未来合法分支必需的数据和权限。

## 8. 验证汇聚不是用例数量汇总

以设计验证项为入口，关联可执行 Case、所需环境、实际 Run 与原始证据；四者各有稳定标识和责任，复用现有测试规范/记录，不新增并行台账。
逐项检查正常、异常与跨字段要求如何被承接；Case 名称或测试脚本存在不算已经执行。
未实现用例、已实现但 NOT_RUN、执行 BLOCKED/FAIL，以及有裁剪依据的 N/A 分别统计，不从分母中静默删除未闭合项。

案例 EX-V3→EX-T3→EX-ENV-M/EX-ENV-P 展示同一保证的模型与实际实施边界：模型检查由来源封口事实到取证结论及终态 Guard，不能证明真实 Worker 无旁路写权限。
EX-V6 尚未实现/NOT_RUN，不能因为模型全绿关闭系统要求；每项组合保证都要找到同一基线与配置下的各方和共同证据。

## 9. 修改核心规则后的全篇回查

一条规则给一个 ID 和唯一规范位置，图、状态与接口示例引用它，但引用不能替代内容核对。
改变规则后按“接口请求/响应与错误→状态表/Guard→正常及异常流程图→资源/权限/清理→验证项/Case→系统摘要与下游输入”逐位置检查。
记录规则 ID、受影响位置、已同步内容或无影响理由、反例复验及仍有旧语义的位置；不要只记“全篇一致性 PASS”。

以案例 EX-R6 为例，将释放依赖从全局终结改为已选分支后，要检查取消不再等待 deliver、stop 不反等取证、discard 控制权仍在、
跨字段响应合法、EX-T4 真正覆盖取消。文字中没有旧术语也可能仍保留旧条件；必须走输入和状态变化，不只做替换搜索。
