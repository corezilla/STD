# 设计文档编写规范

## 1. 设计文档的用途

设计文档必须让没有参加前期讨论的工程师看完后能够回答：为什么做、为谁做、做什么、
有哪些页面或接口、数据如何流动、代码放在哪里、如何实现、失败时如何处理，以及怎样验收。
不能只罗列原则、名词、Gate 或模板标题。

本文规定共同写作质量；AI Agent 如何将其转为工作包、预设计、正文和检查，见
[通用 AI 编写指南](ai-authoring-guide.md)及其按模板类型选择的专项。模板仍决定文档的承载结构，
本文保留共同质量要求，AI 指南解释如何执行，不用指南替换模板内逐节建议。

设计同时交付人能读懂的正文与 Agent 能精确检索的契约：
正文成员 ID ↔ 接口目录 ↔ 完整机器定义 → 下游实现与验证。统一标识、目录字段、覆盖/版本和来源分工见[接口与数据规格映射规范](interface-data-mapping-standard.md)。
实际契约不能是 TODO 路径，完整阅读视图从唯一源生成或核对，不能另改一套字段。
系统还须先登记机制 ID、Document ID、预定文件名及依赖，逐份写作时保持映射；Planned 不冒充已成文。

## 2. 编写顺序

建议按以下顺序完成，而不是从架构术语开始：

1. 选择设计对象、写作 profile 和适用范围，明确客户、使用者及主要业务，记录约束、假设与版本/配置/拓扑；
2. 写一个自包含的系统概览，约 1–2 页回答问题、位置、输入处理输出、分工、主路径、版本范围和关键取舍；
3. 列出功能、页面或设备行为，分别标记实现状态和验证结果；
4. 画出系统边界和端到端数据流，分解组件并绑定实现位置、部署与责任人；
5. 展开启动、配置生效、数据平面和停止等重要过程，解释数据、接口、状态、失败恢复和信息安全架构；
6. 将系统结论分配到承接单元，明确固定输入和设计自由度，下级记录落实及组合验证；
7. 写出实现顺序和验收条件，用逐节完成条件检查真实正文，再回看概览是否与细节一致。

`design.system` 主模板据此组织为 17 章：短封面后 §1 仅保留目的/读者与范围，§2 为产品应用与设计目标，
§3 系统概览为所有系统的必需正文，直接包含架构、组成职责和物理/逻辑映射；§14 信息安全
架构按资产/信任边界和入口等条件触发，物理/电气安全由 §15 负责。profile × 章节矩阵和条件
规则见[系统模板 §B.2](../templates/design/architecture-design.md)，不能自行用 N/A 代替裁剪决定。
参考资料、输入基线、裁剪、假设、修订记录和长目录放在文末附录；这是展示顺序，
不表示等写完才核查输入。影响理解的限制和术语解释仍应在相应正文就地说明。
条件不成立时也记录理由、tailoring decision 和批准证据；结构裁剪使用已有 tailored/引用机制。
§5“重要过程”把各模块机制串成完整系统行为，依次为 §5.1 总览与工作模式、§5.2 完整业务
处理、§5.3 启动、§5.4 配置加载与生效、§5.5 停止与重启、§5.6 异常恢复、§5.7 模式切换。
先讲业务便于理解，不表示可跳过启动或配置前提；§17.2 汇总下级详细设计与验收任务，并保留
关联风险与未决项，不把任务登记当作设计、实现或验证完成。

**遇到设计未定时**，先列本节必须解决的问题，做简短预设计：输入与约束 → 可行选项 → 正常
及失败推演 → 推荐方案与代价 → 未决项。简单分析留在相关节，复杂分析复用
`evaluation.technical-analysis`；不要求每章另建文档或新增审批。说明下一次分析/实验要区分
什么选项、需要什么输入及选择判据，缺少外部决定时明确确认责任和受影响工作边界。
推荐不等于批准，选定后将机制、约束和验证方法写回设计，再按已有规则记录重要决定。
关键机制或判定方法未定不能判该节设计完成，但不依赖它的部分可继续；未实现和未实测分别记录。

以上 17 章位置专指 `design.system`。编写 `design.system-mechanism` 时以一项机制为对象，
从机制用途和场景开始，不重新编写整个产品；沿其 15 章主线展开参与方、协议、状态、维护与验证。
机制模板的维护入口在 §11.2、测试在 §14、输入/裁剪在附录 A；不能把本文系统章号机械搬过去。
机制专用工作步骤见[系统机制 AI 编写指南](ai-guides/system-mechanism.md)，
系统全景的执行方法见[系统设计 AI 编写指南](ai-system-design-authoring-guide.md)。

## 3. 强制写作规则

- 使用具体名词，不写“相关模块”“适当处理”“必要时重试”等无法实现或验证的表述。
- 产品场景先说明客户类别、实际使用者、业务任务和部署维护条件，再写操作流程；维护操作
  不能代替主要业务。多客户环境解释差异如何影响功能、容量、隔离和可靠性，固定场景明确边界即可。
- 每项功能必须有输入、处理、输出、失败行为和验收条件。关键功能用连续段落解释对象、判断、
  状态变化、选择理由和代价；用代表输入推演结果，不能把这些要求各填成一句抽象口号。
- 每张图后必须有文字说明；图不能替代字段、状态和错误语义。
- 每张架构图注明 `Current / Target / Transitional`、适用基线/配置/拓扑，并标示责任边界、Owner、
  方向、协议或 IF ID、状态和图例。未来对象采用不同形状/线型及文字标签，不能只依赖颜色。
- 关键能力分别记录实现 `Planned / Partial / Implemented` 与验证 `NOT_RUN / BLOCKED / FAIL / PARTIAL / Verified`。
  Verified 只覆盖其明确版本、配置、能力范围和验收条件；不能由文档 Approved 或代码存在推导。
- 数值注明单位、作用域、条件及 `Modeled / Simulated / Measured` 证据；目标用 Target，外部规格用 Specified
  并标来源。无法确定的数值写 Unknown 和 Owner，不补造数字。
- 页面不存在时记录 `N/A — 无用户界面；Tailoring Document ID / Decision ID；批准记录`；
  CLI/API 等实际功能入口仍需描述。
- API、Schema、IDL、寄存器和配置已有机器定义时引用固定权威来源，不复制成第二份真相。
- 路径、模块、类、进程、表和 topic 应写真实名称；尚未决定时使用带 Owner 的 Open Question。
- 示例是结构示范，提交前必须替换，禁止把 `Example`、`TODO` 或虚构值留在正式文档。
- 系统设计必须自包含地解释用途、结构和工作原理，禁止仅以文档链接、模块清单或需求索引充当设计。
- 系统设计及正式机制/契约须确定完整公共操作、字段、错误、命令和适用的硬件连接，§10
  统一展示或精确关联；不能以“下级细化”留下共同方案空缺。已有机器源按固定版本生成或
  核对展示表，不手工维护第二份规范；没有机器源时可先在受控设计中完整定义 Proposed
  契约，再核对编码与迁出。RTL 内部实现、私有布局和测试步骤仍由下级维护。
- 每种重要模式单独展开场景、图、编号步骤、原理、配置限制和代表失败；关键模块解释接收、
  处理、交付及释放，数据章沿同一阶段 ID 展示对象前后变化。图表用于说明和汇总，不替代正文。
- 重要过程从实际触发和入口写到可判断的结果，逐步说明执行方、前置条件、顺序/并行、状态
  变化、超时和失败出口，并解释启动、配置变更、业务处理与停止相遇时如何裁决。§5 保留系统级
  完整过程视图；独立机制文档唯一维护详细状态转换和参与方协议，系统仍解释端到端原理、
  关键阶段、系统级约束及代表失败，固定引用并核对一致，不能只剩索引。已有升级等流程按
  Process ID 索引，不再复制。数据平面是主要业务路径的视角，不强制新增组件；不具备的
  热更新、多模式等能力保留适用性依据。
- 遇到“独立隔离、原子生效、安全恢复、自动回滚”等结论，要解释参与对象、成立条件、执行
  机制和不成立时的结果。性能和功热从负载推导资源需求；共享资源不能重复计入预算，也不能在
  分析共同失效点时被遗漏。配置、控制、启动及升级保留系统级执行顺序和判据，下级文档只承接具体实现。
- 系统结论通过系统模板 §3.2 的 Constraint ID、固定来源及条件分配到单元；机制模板 §3.1、
  通用单元模板 §1.1 及硬件/FPGA 专项模板 §1.1 记录承接、自由度、落实和验证；专项模板
  §12 关联这些约束，区分本地验证与系统组合验证，不必另建通用文档。共享预算不能重复分配，
  组合关系不能由局部 PASS 推导；冲突回到原决定责任方，不由下游自行放宽。摘要引用契约而不复制字段定义。
- 模板内每处段落式帮助默认折叠，正文写在帮助块外。评审折叠帮助检查真实正文；帮助、示例和工具
  结构 PASS 均不证明章节质量。逐节完成条件与顶部交付检查表由 Reviewer 对照正文判断。
- 可测试性说明主要方法与结果判定、受控故障与恢复、环境快速部署/复位、并发隔离、自动化
  复现及覆盖验收。统计、日志、故障定位和自检要求属于 §11 的可维护性；指示灯、维护/调试
  命令、替代依赖、旁路和环回的接口能力要求属于 §10.4。系统设计明确所需能力、口径、责任
  和验收依据。主要命令类别、执行位置与入口、被控对象、权限、调用流程和结果也必须在系统
  设计阶段确定；公共参数全集及结果契约不可推迟，解析器内部等实现细节由下级承接。
  测试章引用这些能力，不另写一套机制；
  多任务环境隔离与模块局部调试分开说明。
- 硬件制造测试从缺陷、输入与观测、装配阶段和返修定位反推必须预留的产品能力，分配到硬件、
  结构和固件；系统明确可达性、安全与覆盖边界，详细工装和程序由下级维护，不仅列测试名称。
- 按适用能力子项贯通场景、运行时统筹、参与方确认、公共契约及双方验收；工程 Owner 不等于
  运行组件。已有局部定义先核对纳入组合，冲突先解决，不因系统摘要不全而重造机制。
  关键共同方案未定是设计缺口，不能改写为仅待实现/实测；只阻塞受影响依赖，不无界重做全文。
- 新增子节采用通用职责、适用条件及虚构示例。检查目录、路径/依赖、结果汇总与清理属于自检
  设计；跨方统计/日志定义关联、窗口与代次；测试控制定义接受、命中及撤销确认。仅在实际
  产品范围适用，不为填模板新增自检平台、带外通道或通用注入机制。

系统模板的读者复述检查、正反例和信息深度规则见
[`architecture-design-authoring-guide.md`](architecture-design-authoring-guide.md)。它补充模板内指导，
不要求项目日常写作时查询未采用的新模板版本。

## 4. 图和表的最低要求

按设计性质选择最小必要集合：

- 有 UI：页面清单、主要功能页的简要布局或线框图，以及含校验、等待、结果与失败分支的核心用户操作流；
- 有多个组件：组件图和端到端 sequence；
- 有持久化：实体关系或数据表，以及读写 ownership；
- 有生命周期：状态机或状态转换表；
- 有并发或恢复：正常流与失败/恢复流；
- 有硬件/FPGA：功能框图、控制流、数据流、clock/reset 或电源启动关系。

## 5. 可执行性检查

先从正常、异常和维护入口核对接口族/成员覆盖，再实际走 OP→请求/响应→字段→行为正文→下游模块→设计 V/Case。
重复 ID、失效锚点、未解析类型、字段/签名/错误/默认值错配、旧消费基线须有具名反例检查；
静态检查与作者自审、独立评审、真实运行验证分别记录，不能用一项 PASS 代替另外三项。


设计进入实现前，Reviewer 应能够从文档中直接得到：

| 检查项 | 通过条件 |
|---|---|
| 问题 | 能说明不实现会造成什么具体影响 |
| 功能 | 每项功能有唯一 ID 和验收条件 |
| 页面 | 页面、路由、状态和操作明确，或说明 N/A |
| 数据流 | Producer、处理步骤、存储和 Consumer 明确 |
| 实现位置 | 映射到计划新增或修改的真实路径 |
| 异常 | timeout、权限、空数据、重复和部分失败有结果 |
| 验证 | 每项关键功能可映射到测试或人工验收步骤 |
| 承接 | 固定约束、条件与自由度明确，下级落实可追踪，资源与行为按同一基线组合校核 |
| 未决 | 关键机制未定时有预设计、具体下一步和阻塞边界，不以登记问题代替设计完成 |

每个适用节统一检查：实际决定了什么、依据是什么、下游必须遵守什么、还能自行设计什么、
怎样检查承接结果？Reviewer 应能定位到正文、分配及验证，不要求每节重抄五个答案或增加形式
表单。无下游分配项时说明该节结果的使用方或边界，不编造承接单元。

任一关键项仍为“待定”时，除 Owner、截止 Gate 和阻塞影响外，还须明确预设计/分析入口、
所需输入及下一步选择判据；设计、实现、实测的完成状态互不代替。
