# STD 编码规范

## 1. 适用范围

本规范定义跨语言的最低工程要求。项目应在 README、开发计划或 tailoring 中声明具体语言、
工具链和必须执行的 formatter/linter/test 命令。语言官方风格与本规范冲突时，由项目
tailoring 记录取舍，不在源码中并存两套风格。

## 2. 基本原则

- 代码首先表达清晰的责任边界，不为缩短行数隐藏状态和副作用。
- 优先扩展已有机制；新机制、新配置路径、新 fallback 或并行实现需要明确设计决定。
- 一个概念只有一个 current implementation authority，不用复制代码维持并行真相。
- 对外行为由 API、Schema、IDL、错误契约和兼容性规则定义，注释不得替代机器契约。

## 3. 命名与结构

- 使用能表达业务语义的名称，避免未定义缩写、`tmp2`、`new_new` 等临时命名。
- 文件、包、模块和类的责任应单一；跨 Owner 机制不藏在单个内部 helper 中。
- 公开 API 不暴露未批准的内部实现细节。
- 生成代码、手写代码和第三方代码必须在目录或文件头上可区分。

## 4. 格式与静态检查

- 每种语言选定一个 formatter 和一组 linter，版本受项目工具链锁定。
- CI 和本地使用同一命令；禁止 CI 安静改写源码后再判定通过。
- 禁止尾随空格、未解析 merge marker、提交编辑器临时文件和平台元数据。
- 格式化变更与行为变更尽量分开，保持 diff 可审阅。

## 5. 错误、日志与输入

- 不吞掉错误；要么在当前边界处理，要么保留语义向上传播。
- 错误分类、错误码和重试性必须与契约一致；不从日志文本反向推断机器状态。
- 所有外部输入在信任边界校验，内部类型不得被当作未验证输入的替代品。
- 日志不记录 password、token、secret、完整凭据、未脱敏个人数据或大型 payload。

## 6. 状态、并发与恢复

- 状态转移要有显式前置条件、结果和失败语义。
- 并发共享状态必须声明 ownership、synchronization 和 cancellation 边界。
- 重试、幂等、去重、超时和未知结果必须有稳定 key 和可测语义。
- 恢复代码不得绕过正常权限、审计、契约或状态机。

## 7. 依赖与兼容性

- 依赖必须由锁文件或等价机器清单固定，不在构建时无约束取“最新”。
- 新依赖需记录用途、许可证、安全边界和取消方案。
- 公开契约变更必须根据项目兼容性政策分类，并用 fixture 或 contract test 固定。
- 不为通过旧测试无限叠加未记录的 compatibility branch。

## 8. 测试要求

- 修复缺陷时增加能在修复前失败、修复后通过的回归测试。
- 外部契约变更至少覆盖正向、边界和拒绝路径。
- 静态通过不等于 runtime 通过；未运行的环境或外部测试必须记为 NOT_RUN/BLOCKED。
- 测试不依赖生产 secret、个人账号或无法重建的手工状态。

## 9. 注释与文档

- 注释说明为什么存在约束、特例或取舍，不逐行翻译代码。
- TODO/FIXME 必须有可追踪的 issue、Owner 或明确删除条件。
- 影响架构、契约、部署、恢复、安全或运维的代码变更必须同步对应权威文档。

## 10. Review 与例外

代码变更提交前至少执行项目指定的 formatter、linter、相关测试和 diff/whitespace 检查。
评审重点是行为、边界、错误、恢复、安全、兼容性和测试，不只检查格式。

无法遵循的条款必须在 tailoring 或批准的 ADR 中记录原因、风险、Owner、适用范围和
结束条件；临时例外不自动变成长期标准。
