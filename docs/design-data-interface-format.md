# 设计数据结构、接口与系统错误码描述规范

版本：1.2.0-draft.2 · 日期：2026-09-25 · 状态：STD 方法；项目须明确采用对应 STD 基线

## 1. 目的与纵向承接

系统设计通过**公共数据结构、接口成员和系统错误码**把总体决定传给机制、子系统、模块、ISD、实现和验证。每层必须说明自己拥有的对象与操作，以及继承的 ID、固定来源、允许细化的范围和验证责任。只写职责表或链接目录，不能证明上下级可按同一契约编码。

逐项建立以下双向关系：`系统 Data/Type/Error ID 与 Interface Member ID → 机制/契约 → 子系统 → 模块 → ISD/代码 → V/Case/Run`。不存在的中间层可跳过，但不得跳过真实提供方或消费方。上级已定的含义、范围、字段、错误和生效保证不能在下级重新发明；下级发现缺口须以原 ID 和具体反例反馈。

本规范与[接口与数据规格映射规范](interface-data-mapping-standard.md)同时适用。Schema、IDL、OpenAPI、Proto、头文件、RTL、register map 等已存在机器源时，它们拥有类型、字段、签名和编码的机器权威；正文保存同一固定基线的完整阅读视图和行为解释，须由源生成或逐项核对。没有机器定义时标 `Proposed`，记录形成契约的责任与截止 Gate，不把文档草案当作已可实现的接口。接口目录只定位成员、来源、承接和验证，不建立第二份字段权威。

## 2. 记录型数据结构

六类软件设计文档统一使用主章标题“数据结构设计”（章节编号沿用各模板），并在章内按数据性质选择适用分类，而不是另设数据结构清单或把定义、寿命、实例拆成多个章节。以下八类是分类候选；总体系统模板将运行状态并入业务与操作结构，并将错误码和错误载荷一起放在 §9.1：

1. **公共基础类型与枚举**：例如 `TaskState = QUEUED | RUNNING | DONE`。
2. **业务与操作数据结构**：例如 `InspectionRequest`；同一结构既可作为上游输出，也可作为本层输入。
3. **配置与规则数据结构**：例如 `DetectionPolicy`，说明适用范围、版本与生效点。
4. **通信报文结构**：例如 `FrameReadyEvent`，说明编码、关联身份、顺序与兼容版本。
5. **设备与 FPGA 表项结构**：例如 `RouteTableEntry`，说明字段位宽、复位值、写入与生效条件。
6. **运行状态数据结构**：例如 `TaskRuntimeState`，说明唯一写者、状态转移与恢复事实。
7. **数据库表结构**：例如 `inspection_jobs`，说明列、键、索引、事务边界和迁移。
8. **错误码与错误结构**：例如 `InspectionError` 及 `ERR-REQUEST-CONFLICT`，逐码说明含义与下级使用方式。

这些分类不是项目必须保留的空章节。项目成文时仅保留实际适用类别；不适用类别在章首说明具体原因与 tailoring 依据。每个结构以真实名称为小节标题，完整记录 ID、唯一来源、字段、约束、状态/所有权/寿命、合法与拒绝实例以及验证。继承结构只定位原定义和本层投影，不复制字段；跨结构关系另用图或短表分析，不形成第二份定义。模板可在分类之后增加本层特有的跨结构分析：总体系统在同一节描述业务数据和伴随元数据的流转，再展开状态表与容量，不另设公共编码章节；软件系统展开业务变换、持久化/缓存/迁移；机制展开交接可见性；子系统展开组织与阶段变换。总体系统的错误码和错误载荷均由 §9.1 统一定义，不再另设错误结构小节。不同层级的设计粒度不同，但同一字段的含义和机器权威不能随章节变化。无直属子系统时，系统可直接把 ID 分配给模块。

结构定义不要求罗列全部调用方或函数。交互由架构、流程和接口章节自上而下表达；结构拥有者在唯一来源定义字段，消费者只记录用途及必要投影。这样修改一个内部调用点不必更新多份数据定义。

本文拥有或必须完整呈现的数据对象使用固定字段段落；状态转换、多对象比较等矩阵仍用表格。每条记录至少说明：

- 稳定 Data/Type ID、名称、定义、适用范围、唯一机器源或 `Proposed` 决定来源；
- 逐字段 ID/名称、类型或引用、必填/缺省/可空、范围/枚举/单位、长度/计数来源、条件有效性及含义；仅实际二进制/RTL 布局补位宽、端序、对齐、复位值等；
- 键、跨字段不变量、生产/消费、唯一写者、可见时点、所有权与寿命，适用时补持久化/迁移；
- 一条合法和一条边界/拒绝实例，以及验证项和来源核对结果。

公共结构只在唯一来源完整定义；其他文档用 ID、版本/revision/hash/selector、用途和必要投影引用。确需转化时逐字段说明保留、增加、丢失、校验和转换责任。不得用统一排版符号代替实际字段校验，也不得把特定时间精度、时区或可空记法强加所有项目。

## 3. 接口设计的统一结构

六类软件设计文档的接口主章统一使用标题“接口设计”（保留各模板原章节编号），**按实际接口形态分类、逐接口完整记录**，不设重复的“接口清单”，也不把同一接口的定义、交互、异常和示例拆散到不同小节。分类入口为：

1. **API**：向使用方提供可调用能力的函数、公开方法、HTTP/RPC 端点等，以真实的限定函数名、签名或路由作标题；代码尚不存在时标 Planned，不伪称真实 symbol。
2. **消息与数据流接口**：组件或系统间为协作而交换的命令、状态、事件、队列消息、流、文件等，以实际端点、topic、消息或流名称作标题。此类通信也可能使用 HTTP/RPC；不能只按传输协议判断类别。
3. **硬件与固件接口**：连接器、总线、寄存器、FPGA 端口等，以实际连接或端口名称作标题。
4. **人机与维护接口**：UI 操作、CLI、诊断入口等，以实际页面操作、命令或入口名作标题。

只保留适用类别；不适用类别按项目 tailoring 说明，不为填模板制造接口。同一接口只在一个类别完整定义一次。分类看设计用途：向使用方提供产品或模块能力的 `POST /jobs` 属于 API；组件间协调租约的 `POST /internal/lease-ack` 即使用 HTTP，也属于消息与数据流接口。两例均为虚构；不得因此把同一 HTTP 端点在两节重复定义。类别不是所有权或调用方维度：例如采集卡的 PCIe 连接和驱动 `AcquireFrame()` 是两个接口，分别定义并以关联 ID 说明关系。系统、机制、子系统、模块、ISD 可按职责增加本层专有字段，但不得把同一接口拆成跨章节的第二份描述。

### 3.1 逐项记录的必需内容

每个本文拥有的接口以**真实可查找的函数、路由、消息或端口名称**为标题。标题下面首先展示完整接口声明，形式尽量贴近项目实际代码、IDL、OpenAPI、消息 Schema 或硬件端口定义：参数按实际顺序列出名称和数据结构类型，成功与错误输出也列出类型；异步接口同时注明受理结果与最终结果。代码已存在时使用真实签名，Planned 接口标明拟定声明及尚未确定的部分，不伪称现有 symbol。声明中的数据结构名是读者查找“数据结构设计”章的主索引；跨文档来源再附精确路径/锚点与版本。不能只给 Data/Type ID 或整章链接让读者自行猜输入输出。

声明之后，输入和输出分别就地展示参数/结果使用到的字段及其在本接口中的作用；类型、范围、编码和字段全集由对应数据结构的唯一权威维护，不手写第二套可漂移的完整结构。每项固定字段的标题独占一行，说明另起一段。随后在同一接口记录内按下列顺序写完：

- Interface/Member ID、用途、提供责任单元、交接边界、规格/实现/验证状态、唯一契约与固定版本；代码已有时写仓库相对文件与实际 symbol，未实现时机器目录的 `location/symbol` 为 null。
- 输入：实际签名、参数或请求 Data/Type ID、必填/范围/跨字段条件、前置状态、授权和校验顺序；字段全集只引用数据结构章或机器源。
- 成功输出：返回值/事件 Data/Type ID、受理/生效/完成/持久/释放等适用证明范围和副作用。
- 错误与异常：逐条件 Error ID、触发事实、结果已知性、已发生或可能副作用、返回载荷和合法下一步。
- 交互与生命周期：实际调用上下文、同步/异步、期限、取消、重复/幂等、并发、流控、资源所有权、版本兼容和停止/释放；只写适用项。
- 同一接口的正常与边界/拒绝实例、独立 V/Case、机器源核对及实际 Run 状态。

实际调用参与方在相应架构图和流程中说明，不逐接口维护全量调用函数反向索引。继承接口引用固定来源和本层附加约束；若本层确实改变输入、返回或错误语义，必须回到唯一契约更新，而不是另写影子定义。分配视图只引用原成员 ID/基线，例如系统机制 §14.3 引用其 §5、模块 §5.3 引用其 §9。

API 的呈现顺序示例（名称、参数和类型均为虚构）：

````markdown
#### submit_detection(request: DetectionRequest) -> DetectionSubmission | SystemError

```text
submit_detection(request: DetectionRequest) -> DetectionSubmission | SystemError
```

- **输入**

  `request: DetectionRequest`。本接口读取 `request_id` 判重、`image_uri` 定位图像、`model_id` 选择模型；字段约束见同文档“数据结构设计 → DetectionRequest”。

- **输出**

  成功返回 `DetectionSubmission`，其中 `task_id` 用于查询，`state=ACCEPTED` 仅表示已受理；失败返回 `SystemError`，各错误条件在下方逐项说明。
````

函数签名在此是接口声明，不是第二份机器契约；已有代码或机器源发生变更时必须核对并同步本阅读视图。

硬件/固件接口在同一记录内加端点、方向、连接器/管脚、位宽、电气、时钟/复位、时序、握手及寄存器约束；消息流加边界、顺序、背压、丢弃/重传；人机维护入口加执行环境、目标选择、权限、反馈、退出与审计。软件函数不填虚构电气参数，硬件连接不套函数签名。跨接口共同的容量或安全政策可单独叙述，但逐接口适用条件与结果仍回写在该接口记录。

## 4. 系统公共错误码是公共数据结构

总体系统设计 §9；纯软件项目的软件系统设计 §7，必须建立**系统公共错误码目录**，逐码列出所有适用的对外码及错误载荷。已有上级系统时，软件系统继承其码，只能定义明确分配给软件层的补充码或映射。仅模块内部使用的私有异常不冒充公共错误；跨系统边界前必须明确映射。机器 Error enum/Schema/catalog 拥有实际代码值、类型和编码；系统设计决定公共含义和调用方行为，并核对机器源。

每个公共错误码使用一条固定记录：

```markdown
**<Error ID> · <稳定代码值或机器来源>**
- 定义与适用范围：<唯一含义；不包括什么>
- 触发条件与判定者：<事实来源、产生责任单元>
- 结果与副作用：<未受理、已受理、结果未知、已完成等适用状态>
- 错误载荷：<类型 ID、必填字段、关联身份、敏感信息边界>
- 调用方动作：<修正、查询、等待、安全重试、停止或人工处理及前提>
- 模块承接：<产生、透传、转换、消费的模块及映射目标>
- 唯一来源与兼容：<机器源 version/revision/hash/selector；或 Proposed 缺口>
- 验证：<触发向量、契约 Case、系统组合验收及实际证据状态>
```

同章维护 `Error ID → 接口成员 → 机制/子系统/模块及使用方式 → 设计 V/Case` 的承接索引，或引用能双向核对的等价项目清单。系统目录定义含义；接口逐失败条件引用该 Error ID；子系统/模块说明何时产生、透传、转换或消费；ISD 落到函数/分支；验证覆盖代码值、载荷、状态、副作用与调用方动作。同码异义、缺码、重复码、下级私自新增公共码或接口引用不存在的码，阻止相应设计范围完成。未实现、未执行仍留在分母中。

## 5. 各模板的必填入口

每份模板对应章节开头必须直接列出本层应描述的对象、接口、粒度、唯一来源和 `N/A` 条件，不能只链接本规范。执行时至少核对：

| 模板 | 数据入口 | 接口入口 | 本层责任 |
|---|---|---|---|
| `design.system` | §9.1–§9.6 按类定义；§9.1 先定义公共错误码与错误载荷；业务数据与元数据流 §9.7、状态与容量 §9.8–§9.9 | §10 按接口类别逐项；系统专有约束留在对应接口内 | 总体公共对象、系统码和跨域交接 |
| `design.software-system` | §7.1–§7.8 按类定义；§7.8 公共错误码；业务变换/持久化/迁移 §7.9–§7.11 | §8 按接口类别逐项 | 软件系统边界与继承/补充系统码 |
| `design.system-mechanism` | §4.1–§4.8 按类定义；编码/一致性 §4.9–§4.10 | §5 按接口类别逐项；§14.3 只分配 | 机制状态、消息和参与方操作 |
| `design.subsystem` | §5.1–§5.8 按类定义；组织/变换 §5.9–§5.10 | §6 按接口类别逐项 | 本层边界对象及直属单元交接 |
| `design.definition` | §6.1–§6.8 按类定义 | §9 按接口类别逐项；§5.3 引用 | 模块公共/私有关键对象与可调用操作 |
| `design.data-dictionary` | §3 按八类逐结构完整定义；§4–§8 仅作跨结构分析与映射 | 不拥有操作接口 | 受控字段阅读视图及机器源映射 |
| `design.implementation` | §4.1–§4.8 按类定义；语言级表示和代码映射随具体结构记录 | §5 按接口类别逐项；错误传播在接口记录内落实 | 私有表示、函数实现、错误落点 |
| `design.hardware` | §3–§5 | §5 | 板级信号、连接器和电气边界 |
| `design.fpga` | §2、§4–§5 | §4–§5 | RTL 端口、CSR、时序与握手 |
| `contracts.specification` | §3–§4 | §2、§5、§8 | 请求/响应/错误数据和完整公共契约 |
| `interfaces.control` | §4 | §2–§3、§5–§6、§9 | 双方数据/命令及物理/传输/版本约定 |

非设计/契约模板按自身用途引用数据/接口 ID，不强制新建两章。目录结构无需为本规范改变。

## 6. 检查与迁移边界

机器可判定的检查覆盖成员身份、来源/角色/覆盖；系统公共错误码可显式运行 `python3 scripts/validate-public-error-catalog <系统设计.md>`，核查逐码必填槽位、重复 ID/代码和同文档接口/下级/验证索引。该检查为新快照的按需 Gate，不静默加入旧项目的默认校验；它不能证明机器源中所有错误值均已列出，审查人仍须将目录与固定源双向核对。语义正确性、实际代码分支、Run 真实性及双方互操作仍须内容与运行验证；数标题或分隔符不等于质量。完整审查用一个具体成功输入和至少一个错误输入双向走查系统决定→接口→下级实现→测试。

STD 发布新快照才让新规则生效；旧项目按锁定基线继续，用户明确要求时才升级。新增模板字段须递增对应 Template Version，STD 发布版本另递增；新检查不可静默让旧项目失败，也不可把 Draft/Proposed 当成已批准契约。
